# 06 · 桌面应用（怎么打开、怎么打包）

> 到这一步，AgentHub 已经是一个**双击就能打开的桌面应用**，不是一个"要敲命令跑起来的脚本"。
> 这篇只讲怎么用、怎么打包，不讲设计取舍（那在 `05-成员接入.md` 里）。

---

## 一、三种打开方式

| 想干什么 | 怎么做 | 适合 |
|---|---|---|
| **像普通软件一样打开** | 双击桌面的 **AgentHub** 图标（或 `release\AgentHub\AgentHub.exe`） | 日常使用 |
| 开发时跑 | `npm run app` | 改了代码要看效果 |
| 只想用网页版 | `npm run ui` 然后在浏览器打开提示的地址 | 调试界面 / 想用浏览器插件 |

桌面图标指向的就是 `release\AgentHub\AgentHub.exe` —— 那是**免安装**的，整个 `release\AgentHub\` 文件夹拷到任何地方（U 盘也行）都能跑。

---

## 二、它启动时到底干了什么

```
AgentHub.exe（Electron）
   └─ 起一个子进程：electron.exe 以纯 Node 身份运行 ui/server.js
        └─ 只监听 127.0.0.1:<端口>，端口被占就顺延（8787 → 8788 → …）
   └─ 从子进程的输出里读到**真实**端口，开一个窗口指过去
```

两个细节值得知道：

- **端口是服务自己决定的**，壳只读它印出来的那一行（`→ http://127.0.0.1:8787`）。
  壳不猜端口 —— 一份逻辑两处实现迟早对不上，这个项目在别处已经吃过一次亏。
- **界面窗口不是网页浏览器**。它连的是本机 127.0.0.1 上的服务，全程不出网（除非你让它调成员）。

关掉窗口时子进程会被一起收掉。如果上一次是**被强制结束**的（任务管理器强杀、断电），
可能留下一个占着 8787 的孤儿服务 —— 那样下次启动会顺延到 8788，功能不受影响。

---

## 三、第一次打开要做的两件事

1. **工作目录**：默认是 `我的文档\AgentHub`。左上角那个名字就是当前工作目录，点它可以换。
   成员只会在这个目录里读写文件（服务端做了路径穿越防护，`..` 出不去）。
2. **成员密钥**：界面右上角「成员」里能看到哪些成员实测可用。
   需要密钥的（豆包 / claude 等）要写在程序目录的 `.env` 里，例如：

   ```
   ARK_API_KEY=你的火山方舟密钥
   ```

   > 服务是长驻进程，**读不到你在某个终端里 `export` 的变量** —— 所以用 `.env`。

## 四、改完代码之后：重新打包

```
npm run package
```

它会做八件事，任何一件不过就整体失败（不会给你一个"看着像好了"的包）：

1. 拷贝 Electron 运行时（跳过 `electron.exe` 与 `resources/`）；
2. **写入图标与版本信息**（`rcedit`），再**自证真的嵌进去了**（解析 PE 资源逐字节比对，见 §八）；
3. 把 `electron/` `ui/` `src/` `package.json` 拷进 `resources/app/`；
4. **依赖闭包检查** —— 把代码里所有相对引用抽出来，逐个确认目标在包里；
5. **哈希比对** —— 拷进去的每个文件逐一核对；
6. 语法检查；
7. 文件计数（有没有残留/多拷）；
8. **用产物自己跑一遍冒烟** —— 启动那个 exe、断言界面真的画出来了、截一张图。

产物：`release\AgentHub\AgentHub.exe`。

> 全绿的判据是最后一行 `打包成功`、退出码 0。
> 如果某一步"**没能跑成**"（而不是跑了发现错），它会明说"没能执行"——
> 那种情况**不算通过**，别把日志里的 ✓ 当全部（§8.7 讲为什么这件事值得单开一节）。

### 为什么要第 3 步（而不是只比哈希）

**哈希只证明"拷进去的对不对"，不证明"该拷的都拷了"。**
曾经有个新加的模块忘了进白名单：源文件检查过、哈希全绿、产物冒烟也过（旧代码本身是好的），
但便携版一启动就崩 —— 因为缺的那个文件根本不在比对循环里。
闭包检查是专门堵这个的，而且它自己也做过反证：把一个被 `import` 的文件挪走，它会当场变红。

## 五、`npm run smoke:electron`

不需要看见界面，也能验收"这个应用是不是真的能打开"。它会：关掉 GPU、
用一次性的数据目录、在一个独立端口上启动，然后断言——

- 本地服务起来并报出端口；窗口加载的**正是**那个地址（端口顺延也要跟对）
- 界面初始化完成（`boot()` 跑完、服务端的数据真的落进 DOM）
- 顶栏 / 主区 / 左栏**有非零尺寸**（元素在 ≠ 画出来了）
- 成员数是**非零真值**（`0/0` 是静态 HTML 里的占位值，能骗过形状断言）
- 渲染进程能调通 `/api/members`，且报的成员数非零
- 截图非空、尺寸正确
- 渲染进程没有 console 报错

截图落在 `.agenthub\screenshots\`。加了 `--exe <路径>` 就测打包产物，不测开发目录。

## 六、已知的边界

- **没有安装程序**。这是个免安装的文件夹，没有开始菜单项、没有卸载器。
  不想要了就把 `release\AgentHub\` 整个删掉，再删掉桌面图标。
- **没有签名**。Windows SmartScreen 第一次运行可能提示"未知发布者"，选"仍要运行"。
- **单实例**：已经开着的时候再点图标，会把现有窗口拉到前面，不会开第二个。
  （开第二个会去抢 8787、顺延到 8788 —— 两个窗口、两份互不相干的状态。）
- **`release/` 是产物，不是源码**。改代码要重新 `npm run package`；直接改 `release/` 里的文件，
  下次打包会被覆盖。
- **`.env` 会被一起打进产物**（如果存在）。里面有 API 密钥，别把 `release\AgentHub\` 发给别人。

## 七、第八轮在壳上修掉的两个真 bug（2026-09-29）

### 7.1 「时好时坏打不开」的根因：loadURL 自己中断自己

症状：双击打开，有时直接看到「AgentHub 没能启动」+ `ERR_ABORTED (-3)`，重开又好了。

根因（从失败页截图上的那一行 ERR_ABORTED 反推出来的）：
服务的启动横幅是**七行独立的 `console.log`**，stdout 分多个 chunk 到达；
而壳原来**每来一个 chunk 都会重新匹配 URL、再调一次 `loadURL`**。
Electron 里后一个导航会打断前一个，被打断的那个以 ERR_ABORTED reject ——
于是走进 catch、`settle(false)`、失败页把真界面顶掉。服务明明起来了。

修复：`navStarted` 标志，loadURL 只发起一次。之前没炸只是时序运气
（URL 行恰好和后面的行合并进了同一个 chunk）—— 又是"依赖时序"的病，这次长在产品代码里。

### 7.2 工作目录不再失忆

症状：在界面上切到自己的项目 → 关掉 → 再打开，**静默回到 `文档/AgentHub`**，
因为 `/api/workdir` 只改进程内存。

修法（谁启动服务谁决定初始目录，所以分两半）：
- **服务写**：`POST /api/workdir` 成功时把新目录写进 `AGENTHUB_STATE_FILE` 指向的文件
  （没设这个环境变量就不写 —— `npm run ui` 手动起时行为不变）；
- **壳读**：`defaultWorkdir()` 的优先级变为
  `AGENTHUB_WORKDIR`（脚本显式覆盖）→ 记录文件（且目录还存在）→ `文档/AgentHub`。
  记录的目录被删了/变成文件了 → 当"没记过"处理，宁可退回默认也不起不来。

落盘位置由壳指定（`userData` 下），smoke 的一次性数据目录天然隔离 ——
测试跑一百遍也不会碰用户真实状态。

### 7.3 冒烟怎么盯住这两处

- ERR_ABORTED：`tests/electron-smoke.mjs` 全链路跑一遍即覆盖（此前它 14/14 绿过，
  但那正是运气好的时候 —— 这类竞态断言只能降低概率，不能根除）。
- 工作目录：smoke 现在**刻意不走** `AGENTHUB_WORKDIR`，而是预写好记录文件走
  "上次记住的那个"那条路（真实用户每天走的路径），并断言 `r.workdir` 等于预写的目录。

## 八、应用图标：从"Electron 的图标"到"我们的图标"（2026-09-29）

便携版打包只是把 `electron.exe` 改名成 `AgentHub.exe`（见 §四），
所以**产物的图标和版本信息都是 Electron 自己的** —— 资源管理器里是个 Electron 图标，
属性面板写着 Electron，作者也是 Electron。功能一切正常，所以没有任何一道关卡会红，
**只有用户能看见**。

### 8.1 三段链路

| 环节 | 文件 | 做什么 |
|---|---|---|
| 生成 | `tools/make-icon.mjs` | 零依赖手写 PNG 编码 + ICO 容器，出 6 个尺寸（256/128/64/48/32/16） |
| 嵌入 | `tools/package-app.mjs` 第 2.5 节 | 调 `tools/vendor/rcedit.exe` 设图标 + 版本信息 |
| 自证 | `tools/verify-exe-icon.mjs` | 解析 PE 资源树，逐字节比对 exe 里**实际使用**的图标与 .ico |

图形是**六边形轮廓 + 赛博霓虹**：深色底（`#070a16` → `#141830` 的暗蓝紫渐变），
外圈一道霓虹亮边，中间是**枢纽符号** —— 几个发光节点连成一张网。
配色与界面同源（青 `#22d3ee` → 紫 `#a78bfa`）但饱和度拉满，末端补一段品红
（`#ff2cbe`）压住右下角：图标是"深色底上的一束光"，界面里那组偏柔和的品牌色
直接当光用会发灰。
生成过程**无随机数**，同尺寸两次生成逐字节相同 —— 这是逐字节校验的前提。

> 2026-10-01 一天之内改了三版，每一版都是被**小尺寸**逼出来的：
>
> 1. 最初的"主脑 + 三个成员"（中心节点 + 三个卫星 + 三条连线）：资源管理器列表与
>    任务栏要的是 32px / 16px，那个尺寸下四个点加三条线只剩一个白团，看不出画的是什么；
> 2. 换成"六边形 + 白色字母 A"：字形轮廓在同样的像素预算里信息量大得多，
>    大小尺寸都认得出 —— 但 A 只是首字母，不表达产品在做什么；
> 3. 现在这版：回到节点 / 网络的语意（"一个主 Agent 编排若干子 Agent"就是它的
>    字面样子），改成**深色底 + 发光线**。亮线自己就是轮廓，既不吃字形也不吃实心色块，
>    线宽和节点大小还能各自调，比字形好"喂"给像素。
>
> 外轮廓始终是六边形：周长比圆角方块短、顶点更少，抗锯齿要磨的边也少，
> 小尺寸反而更实，而且一眼就是"芯片 / 元件"。

> 图形是**有符号距离场**逐像素判定出来的，不是位图素材：外框用"到六条边的距离"
> （`hexIn`），连线是胶囊形（点到线段距离），节点是圆。符号只取**离得最近的那个**
> 特征上色（距离场的并集），所以节点压在连线上的接口处不会出现颜色镶边。

### 8.2 为什么手写图像编码，不用图像库

本机装火绒，`npm install sharp / jimp / png-to-ico` 会拖很久还可能半装。
而需要的东西标准库就够：PNG = `node:zlib` + 每块一个 CRC32；
ICO = 6 字节头 + N×16 字节目录 + 各尺寸 PNG 原样塞进去（Vista 以后允许条目直接是 PNG）。
整个生成器零依赖、离线可跑。同理，`rcedit.exe`（MIT，electron 生态在用）
直接拷进 `tools/vendor/`，不为一个 150KB 的工具去跑 npm。

### 8.3 ≤20px 单独一档：不是审美，是像素预算

16px 下连线只有约 1 个像素宽，细线会被抗锯齿磨成一圈灰边，远看就是"糊"。
所以 ≤20px 做三件事，**图形本身不变**：

- 连线加粗（半宽 `0.015 → 0.028`）、节点放大（中心节点半径 `0.115 → 0.150`）；
- 节点从 6 个减到 3 个 —— 6 个点在 16px 上会挤成一片；
- **光晕全关**：光晕在 16px 上只有 1 个像素宽，渲染出来是一圈灰边，把本来就不多的
  对比度吃掉；关掉它，亮的就是亮的、暗的就是暗的。

小图标识别的关键是轮廓的对比度，不是细节。
`node tools/make-icon.mjs --sheet <路径>` 出一张对照图：原大小一行 + 16px 放大 4 倍一行，
用来判"小尺寸糊没糊"。**"256px 下好看"是最没信息量的一句评价。**

### 8.4 自证关卡怎么防假绿

`verify-exe-icon.mjs` 最危险的失败方式是**安静地返回空集**（RVA 换算错、资源树没走对），
那样"我们的图标不在里面"恰好为真 —— 检查全绿但什么都没查。所以：

- 必须找到 PE 签名、资源表、`RT_GROUP_ICON`（≥1 条）、`RT_ICON`（≥1 条），缺一即红；
- 比对走 `RT_GROUP_ICON` 列出的 id 找 `RT_ICON`，即**Windows 实际显示的那份清单**，
  而不是"资源里有没有长得像的块"（老图标残留同样能骗过后者）；
- 断言 `exe 实际使用的条目数 == ico 条目数`，且每一块逐字节相等；
- 顺带验版本资源里 `ProductName`（"图标对了但属性面板还写着 Electron"同样是只有用户能看见的失败）。

**阳性对照**：对 `node_modules/electron/dist/electron.exe` 跑一遍 ——
它有自己的图标，断言 `groupCount ≥ 1`、`rtIconCount ≥ 1` 但**匹配 0 条**。
这同时证明了解析器真的在解析，以及"不是我们的图标"真的会被判红。

### 8.5 承重验证（变异 M14）

把 `package-app.mjs` 里的 `--set-icon` 参数删掉（模拟"忘了嵌图标"），重跑打包：

```
  ✓ 图标与版本信息已写入 AgentHub.exe（ProductName/FileDescription/0.1.0）
  ✗ 图标自证未通过 —— exe 里的图标不是我们的
    ✗ exe 实际使用的图标条目 4 个 ≠ ico 的 6 个
  ✓ 依赖闭包检查：51 处引用，全部能在产物里找到
  ✓ 哈希比对：30 个代码文件逐一核对通过
  ✓ 语法检查：17 个 JS 文件全部通过
打包有问题：1 项
```

**rcedit 的退出码是 0、版本信息也写进去了，其余三道关卡全绿** ——
没有这道新关卡，这一版会带着 Electron 的图标发出去。这就是它承重的证据。

### 8.6 窗口图标与任务栏身份

`electron/main.js` 里 `BrowserWindow({ icon })` 用的是**同一个 .ico**（`ui/public/agenthub.ico`），
路径故意写成相对当前文件的字面量（`'../ui/public/agenthub.ico'`），
这样打包脚本的**依赖闭包检查**能扫到它 —— 图标没拷进产物会当场红，
而不是"exe 有图标、窗口没图标"。另外补了 `app.setAppUserModelId('AgentHub')`：
不设的话便携版以 exe 路径为身份，换个目录/文件名，钉在任务栏上的图标就变成白纸或重复项。

### 8.7 别让"环境"决定关卡跑不跑（2026-09-30）

这一节的由来：某次打包的输出是「打包有问题：3 项」——

```
  ✗ rcedit 失败：EBUSY（重试 4 次仍失败 —— 杀软长期占用或环境不允许 spawn 子进程）
  ✗ 图标自证未通过 —— exe 里的图标不是我们的
  ✗ 语法检查失败 17 个
      electron/main.js:
      ui/public/app.js:
      ui/server.js:
```

**三项全是假的。** 逐条核实：13 个 JS 文件手工跑 `node --check` 全部 ok；
"图标不是我们的"更离谱 —— 那次 `rcedit` 根本没跑起来，exe 里当然还是 Electron 的图标。

这就是**假红**。它和假绿一样有害，只是方向不同：假绿让 bug 溜出去，
假红让你去查一个不存在的问题 —— 上面两条会让你去查 `.ico` 和 `rcedit`，
第三条（`electron/main.js: ` 冒号后面是空的）会让你怀疑代码。**照着它改只会白改。**

#### 8.7.1 根因：`spawnSync` 的 stdin 管道

把 EBUSY 归给"沙箱不让 spawn 子进程"是**错的**。实测同一个 `node --version`：

| `stdio` | 结果 |
|---|---|
| 默认（stdin/stdout/stderr 三个都是 `'pipe'`） | `error=EBUSY, status=null` |
| `'inherit'` | `status=0` |
| `'ignore'` | `status=0` |
| `['ignore', 'pipe', 'pipe']` | `status=0`，**且 stdout 收得回来** |

结论：**能 spawn，只是不能给 stdin 建管道。** stdout/stderr 走管道完全正常，
所以"忽略 stdin"和"收回输出"可以同时要。

修法就是三个字段：

```js
spawnSync(cmd, args, { encoding: 'utf8', stdio: ['ignore', 'pipe', 'pipe'] })
```

> 顺带一提：`tests/electron-smoke.mjs` 起 Electron 用的是 `stdio: 'inherit'`，
> 一直跑得好好的 —— 这条线索当时就在眼前，只是没人把它和 rcedit 那两行联系起来。
> **"同一个仓库里有的 spawn 能跑、有的不能"，本身就是个该停下来看的信号。**

#### 8.7.2 修法之二：能进程内做的，就别 spawn

spawn 是**关卡的可失败依赖**：多一层进程，就多一种"关卡没跑成"的方式。
所以顺手把两处改成进程内：

- **图标自证**：`verify-exe-icon.mjs` 本来就导出了 `verifyExeIcon(exeBuf, icoBuf)`
  （`tests/icon.test.mjs` 一直在 import 它），打包脚本直接调它就行 ——
  没必要为了"跑一个函数"去起一个进程。
- **语法检查**：`node --check` 干的事是"解析一遍"，`new vm.Script` 在同一个进程里
  干的是同一件事。产物是 `"type": "module"`，而 `vm.Script` 只认 CJS 语法，
  所以 ESM 分两档退：`vm.SourceTextModule`（需要 `--experimental-vm-modules`）→
  Node 22 内置的 `stripTypeScriptTypes`（它本来是剥 TS 类型注解的，
  但**剥之前必须把整份源码解析一遍**，语法错当场抛 —— 实测
  `const a = (1` → `Expected ',', got '<eof>'`）。
  两档都够不着才如实报"这几个没验"，**不假装通过**。

修完的输出：

```
  ✓ 图标与版本信息已写入 AgentHub.exe（ProductName/FileDescription/0.1.0）
  ✓ 图标自证：exe 实际使用 6 条，逐字节匹配 6/6（ico 尺寸 256/128/64/48/32/16）
```

#### 8.7.3 三条可以搬走的规矩

1. **`r.error` 和 `status !== 0` 必须分开报。**
   前者是"没跑成"，后者是"跑了、发现错"。混在一起时，前者的**空 stderr**
   会伪装成"一堆语法错"，于是你拿着一份没有内容的报错去改代码。
2. **"未能执行"是第三种状态，不能算绿、也不该混进"失败"计数。**
   悄悄算绿会漏掉真检查；混进失败会把排查引向错误的方向（比如去查 `.ico`）。
3. **改完别只信日志，去看那条一直 skip 的测试有没有开始跑。**
   这一轮改完 stdio，单元测试从 `245 通过 / 1 skip` 变成 `246 通过 / 0 skip` ——
   那条 skip 正是 `icon.test.mjs` 里"环境不让 spawn rcedit"。
   **一条长期被跳过的测试开始真跑了，比任何日志都说明问题。**
