## 0. 一句话目标

把本机已有的 6 个 AI agent（WorkBuddy / Claude / Cursor / Qoder / Trae / 豆包）统一接入同一个工作台，**由 WorkBuddy 当主脑做任务拆解与角色分配**，其他 agent 当执行手；每个 agent 既能各自单独使用，也能组成一条自动协同的流水线。

## 1. 已确认的决策（决策记录）

| # | 决策项 | 取值 | 理由 |
|---|---|---|---|
| D1 | 编排大脑 | **WorkBuddy** | 它有本地文件访问权、资料库、专家技能，规划与文档能力是六者里最强的 |
| D2 | 协同模型 | **主从编排** | 主脑动态拆解任务 → 分派给多个成员 → 收集结果 → 汇总定稿 |
| D3 | 产品形态 | **Electron 桌面应用** | 复用已有经验（Claude Desktop / DSH），能起子进程、能常驻托盘 |
| D4 | 人工介入 | **权限可切换**（分档位，对齐 WorkBuddy 的 Ask/Plan/Agent 模式） | 不同任务风险不同，不能一刀切 |
| D5 | 对接方式 | **A · MCP 桥接** | Electron 应用对外暴露 MCP server，WorkBuddy 连上后即可指挥它 |
| D6 | 实施节奏 | **两期** | 先写 WorkBuddy 技能跑通逻辑，验证可行后再包 Electron 壳 |

## 2. 核心概念

| 概念 | 定义 |
|---|---|
| **主脑（Orchestrator）** | 唯一的核心调度者。当前固定为 WorkBuddy。负责：理解目标 → 拆子任务 → 给每个子任务分配成员和角色 → 决定依赖顺序 → 汇总成果 |
| **成员（Member）** | 一个可被调用的 agent。有 id、显示名、启动方式、能力标签、权限换算规则 |
| **任务（Task）** | 用户提出的一个目标，如"给这个模块加单元测试并写说明文档" |
| **子任务（Subtask）** | 主脑拆出来的最小执行单元，绑定「一个成员 + 一个角色 + 一段 prompt + 一组输入产物」 |
| **角色（Role）** | 子任务里的分工标签，如 `代码主笔` / `文档书写` / `评审` / `测试`。由主脑**运行时决定**，不是预设死 |
| **成果物（Artifact）** | 子任务的产出，分两类：文件类（改了仓库里的文件）、文本类（一段文字/报告） |
| **运行轨迹（Trace）** | 一次任务的完整执行记录：谁在什么时候收到什么、输出什么、耗时多久、有没有报错 |

## 3. 成员接入规格

### 3.1 接入能力矩阵（已查证）

| 成员 | 启动方式 | 静默执行 | 流式输出 | 结构化输出 | 能否改文件 | 认证方式 |
|---|---|---|---|---|---|---|
| **WorkBuddy** | 主脑，不通过 CLI 调用 | — | — | — | ✅ 本地文件操作 | 已登录 |
| **Claude** | `claude -p "<prompt>"` | ✅ | ✅ `stream-json` | ✅ | ✅（需权限参数） | 本机已装 |
| **Cursor** | `agent -p "<prompt>"` | ✅ | ✅ `stream-json` | ✅ | ✅ `--force` / `--yolo` | `CURSOR_API_KEY` |
| **Qoder** | `qodercli -p "<prompt>"` | ✅ | ✅ `stream-json` | ✅ | ✅ `--yolo` | 账号登录 / Token |
| **Trae** | ⚠️ 待实测，两条候选路径 | 待验证 | 待验证 | 待验证 | 待验证 | 待验证 |
| **豆包** | REST API `ark.cn-beijing.volces.com/api/v3` | ✅ | ✅ SSE | ✅ | ❌ **无文件能力** | `ARK_API_KEY` |

**Trae 的两条路（第一期实测后二选一）**
- **路径 1**：IDE 自带的 `trae` 命令 —— 网上有说法称支持 `trae agent --prompt`，但信息源不可靠，**需要实测**
- **路径 2**：字节开源的 `trae-agent`（命令是 `trae-cli`）—— Python 包，支持多 provider（含豆包），有 trajectory JSON 输出，**这条更可信**

**豆包的关键限制**
它只是一个模型 API，**没有文件读写和 shell 能力**。所以它在协同里只能承担纯文本角色：文档书写、翻译、摘要、方案评审意见、文案。这反而正好对上你说的"谁为文档书写"。

### 3.2 能力标签（供主脑分派时判断）

每个成员打这几个标签，主脑据此决定派谁：

| 标签 | 含义 | 谁有 |
|---|---|---|
| `code` | 能读改代码仓库 | Claude / Cursor / Qoder / Trae |
| `shell` | 能执行命令 | Claude / Cursor / Qoder / Trae |
| `doc` | 适合长文写作 | 豆包 / Claude / WorkBuddy |
| `review` | 适合评审挑错 | Claude / Qoder |
| `local-ctx` | 能访问本机项目上下文 | 全部（通过共享工作目录注入） |
| `free` | 不额外计费（走已有订阅） | 除豆包外全部 |

⚠️ **假设**：我用上面这套标签体系。如果你想让主脑按别的维度选人（比如"最强模型优先"或"最便宜优先"），告诉我。

## 4. 功能需求

### FR-1 成员接入层（适配器模式）

- 每个成员一个**适配器**，对外暴露统一接口：
  ```
  run(member_id, prompt, workdir, permission_level, context) -> Result
  ```
  统一接口内部负责：拼启动命令、选参数、解析 stdout、归一化成统一结果结构。
- 统一结果结构至少含：`status`（成功/失败/超时）、`text_output`、`changed_files[]`、`tokens/cost`（能拿到就拿）、`raw_log`。
- 适配器**必须可独立调用**（这是"单独使用"的底座）。
- 新增成员只需加一个适配器 + 一行配置，不改引擎。

### FR-2 独立使用模式

- 能在不经主脑的情况下，直接选一个成员对话/执行。
- 每个成员可开多个独立会话，互不干扰。
- 独立会话与协同任务**共用同一套权限档位和日志**。

### FR-3 主从编排引擎（核心）

流程：

```
用户给目标
   ↓
主脑（WorkBuddy）理解目标 + 读取项目上下文
   ↓
拆解成 N 个子任务，每个指定：成员 / 角色 / prompt / 依赖 / 期望产出
   ↓
按依赖顺序调度（无依赖的并行跑）
   ↓
收集每个子任务的成果物 + 状态
   ↓
失败则：重试 / 换人 / 上报给你（按权限档位）
   ↓
主脑汇总成最终交付物
   ↓
落盘 + 生成运行轨迹报告
```

必须支持：
- **依赖编排**：子任务 B 可以用子任务 A 的产出当输入（这就是你说的"谁主要工作 → 谁写文档"）
- **并行执行**：无依赖的子任务同时跑，节省时间
- **失败策略**：超时、非零退出、无输出三类失败要分别处理，且可配置重试次数
- **可中途干预**：按权限档位，可在子任务边界暂停，让你确认/改指令/换人

⚠️ **假设**：主脑拆解结果我会先渲染成一张**执行计划表**给你看（谁干什么、什么顺序），你点确认才开始跑。这对应你选的"关键节点确认"档位。如果那个档位下你想要全自动，改配置即可。

### FR-4 上下文与成果物管理

- **共享工作目录**：所有成员在同一个项目目录下工作，靠读文件自然获得上下文。
- **任务简报文件**：每个子任务生成一份 `TASK.md`，含目标、约束、上游产物路径；直接放进工作目录，成员自己读。
- **成果物收集**：跑完后 diff 出改动的文件，快照存档，可按子任务回溯。
- **冲突处理**（关键风险，见 §8 R2）：
  - 并行子任务若都会写文件，默认**不共享工作目录**，改用隔离副本（Qoder 支持 `--worktree`，其他用目录拷贝）
  - 只有明确串行依赖的子任务才共享同一目录

### FR-5 权限与人工介入

对外只暴露三个档位（对齐 WorkBuddy 的 Ask / Plan / Agent 模式）：

| 档位 | 行为 | 换算到各 CLI |
|---|---|---|
| **只读（Ask）** | 成员只能分析、只出建议，绝不落盘 | 不加任何提权参数；豆包天然如此 |
| **计划（Plan）** | 给出改动方案，等你确认后才落盘 | 第一遍不加 `--force`/`--yolo`，确认后带参重跑 |
| **执行（Agent）** | 直接改文件，只在危险动作前拦 | 加 `--force`（Cursor）/ `--yolo`（Qoder）/ 对应权限参数 |

- 权限档位**可以按任务设，也可以按成员设**（比如：Cursor 允许直接写，Trae 只允许出计划）。
- "危险动作"至少要能拦住：删除文件、`git push`、安装依赖、访问工作目录之外的路径。

### FR-6 自定义成员（可自加）

- 一个配置文件（建议 `members.json` 或 `members.yaml`）描述成员：
  ```json
  {
    "id": "my-agent",
    "name": "我的 Agent",
    "command": "myagent",
    "args": ["-p", "{prompt}"],
    "workdirFlag": "-w",
    "outputFormat": "text | json | stream-json",
    "permissionFlags": { "readonly": [], "plan": [], "execute": ["--yolo"] },
    "capabilities": ["code", "shell"],
    "env": { "MY_API_KEY": "..." }
  }
  ```
- 新成员接入**不需要改代码**，改配置即可。
- 配置里**不存明文密钥**，走环境变量引用。

### FR-7 可观测性

- 每个子任务：完整命令行、stdout/stderr 原文、耗时、退出码。
- 每个任务：一张执行轨迹（谁→谁→谁，各耗时多少，哪一步失败）。
- 日志按任务分目录存盘，可导出。
- 实时看到每个成员的当前状态（排队/运行中/已完成/失败）。

### FR-8 任务历史与复用

- 保留历史任务，可重跑、可复制某条子任务的命令。
- 可把跑通的一次编排**存成模板**（如"新功能开发标准流程"），下次直接套。

## 5. 非功能需求

| 项 | 要求 |
|---|---|
| **平台** | Windows 11 优先（本机环境），架构上不排斥跨平台 |
| **本机环境兼容** | 必须绕开火绒实时防护、被封的 `reg.exe`、Electron 沙箱限制（详见项目环境备忘） |
| **长任务** | 单个子任务可能跑十几分钟，MCP 回传必须走**异步轮询 + 进度推送**，不能同步等 |
| **可中断** | 任何时刻能停掉某个成员的子进程，且不留孤儿进程 |
| **密钥安全** | API Key 只走环境变量，不进配置文件、不进日志 |
| **离线降级** | 某个 CLI 不可用时，仪表上要明确显示"不可用+原因"，不影响其他成员 |

## 6. 技术架构（A 方案落地）

### 6.1 组件

```
┌─────────────────────────────────────────────┐
│              WorkBuddy（主脑）                │
│  读取项目 / 拆任务 / 分派 / 汇总 / 写文档       │
└──────────────────┬──────────────────────────┘
                   │ MCP 协议（stdio 或 HTTP）
                   ▼
┌─────────────────────────────────────────────┐
│        Electron 应用（AgentHub）              │
│  ┌───────────────────────────────────────┐  │
│  │  MCP Server   ← 暴露工具给 WorkBuddy    │  │
│  ├───────────────────────────────────────┤  │
│  │  编排引擎（调度/依赖/重试/权限）          │  │
│  ├───────────────────────────────────────┤  │
│  │  适配器层（每个成员一个）                │  │
│  ├───────────────────────────────────────┤  │
│  │  工作目录与成果物管理                    │  │
│  ├───────────────────────────────────────┤  │
│  │  监控台 UI（主进程 + 渲染进程）           │  │
│  └───────────────────────────────────────┘  │
└──────────────────┬──────────────────────────┘
                   │ 起子进程 / HTTP
                   ▼
     Claude CLI · Cursor CLI · Qoder CLI ·
     Trae CLI · 豆包 API
```

### 6.2 MCP 工具设计（初稿）

| 工具名 | 作用 |
|---|---|
| `list_members` | 返回所有成员及其状态、能力标签、是否可用 |
| `dispatch_task` | 提交一个子任务给指定成员，立即返回 `task_id`（异步） |
| `get_task_status` | 查询某子任务状态与进度 |
| `get_task_result` | 取子任务结果（文本 + 改动文件清单） |
| `run_collaboration` | 提交一个**完整协同流程**（目标 + 成员清单 + 权限档位），由主脑拆解后执行 |
| `get_collaboration_report` | 取整个协同流程的轨迹报告 |
| `cancel_task` | 中止某子任务 |

**注意**：`dispatch_task` 和 `run_collaboration` 必须是**异步**的 —— 立即返回 id，结果靠轮询。这是为了避免 MCP 调用超时（子任务动辄十几分钟）。

## 8. 风险与待确认

| # | 项 | 说明 | 应对 |
|---|---|---|---|
| **R1** | **Trae 接入方式不确定** | 网上信息源不可靠，IDE 自带 CLI 的能力存疑 | 第一期实测两条路径，都不行就降级为"人工介入成员" |
| **R2** | **并行写文件冲突** | 多个 agent 同时改同一目录必然打架 | 默认隔离副本，仅串行依赖共享目录 |
| **R3** | **豆包无文件能力** | 它只能处理文本 | 主脑分派时限定它只接文本类角色 |
| **R4** | **MCP 长任务回传** | 同步等待会超时 | 全异步 + 轮询 + 进度推送 |
| **R5** | **各家 CLI 参数会变** | Cursor/Qoder 的 flag 版本间有差异 | 适配器启动时自检版本，参数写配置不写死 |
| **R6** | **本机火绒拦截** | 子进程频繁读写文件可能被拦 | 第一期实测；必要时给工作目录加白名单 |
| **R7** | **成本不可控** | 全自动跑可能大量消耗额度 | 每个成员设单次任务 token/时间上限 |
| ⚠️ | **"单独使用"的具体形态** | 我理解为"单成员独立会话面板"，但也可能指"整个工具能当单 agent 界面用" | **需要你确认** |
| ⚠️ | **成果物冲突时谁说了算** | 两个成员都改了同一文件 | 我默认"按依赖顺序后者覆盖前者 + 全部保留快照" |
| ⚠️ | **项目名称** | 暂用 `AgentHub` | 需要你定 |

## 9. 明确不做的事（本期范围外）

- 不做账号体系 / 多人协作 / 云端同步
- 不接管各 IDE 的图形界面（不模拟点击、不逆向它们的插件）
- 不做模型微调或自建模型服务
- 不自建代码索引 / RAG 检索（用成员自己的代码理解能力）
- 不做移动端
