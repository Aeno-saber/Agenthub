# 成员接入

> 2026-09-29 · 把外部 agent 接进 AgentHub 的标准做法与本机实测。
> 本文只讲**怎么把一个成员接进来**；协同调度机制见 [04-MCP桥接验证.md](04-MCP桥接验证.md)，
> 成本见 [03-成本模型.md](03-成本模型.md)。
>
> **原则**：可用性一律以实测为准，不看 `members.json` 里的 `enabled` 字段。

---

## 一、接入一个成员的四步

1. **找到可编程入口** —— CLI 子命令？REST 端点？SDK？三者都没有就没法接。
2. **选适配器类型** —— 标准 CLI 走 `generic`，特殊交互写专用适配器。
3. **写进 `members.json`** —— 命令、prompt 传递方式、权限参数、超时。
4. **跑三层冒烟** —— L1 装没装 / L2 能不能干活 / L3 产出有效
   （详见 skill `windows-agent-cli-headless`）。

第 1 步是最容易想当然的地方。本项目已经栽过两次：

- **豆包**：以为 npm 上有 CLI，实测 `@volcengine/arkclaw` 的 `bin` 字段是空的。
- **Trae**：IDE 自带的 `trae-cn` 是 VS Code 风格的启动器，不是 agent。

---

## 二、两种适配器

适配器契约只有两个方法（`src/adapters/base.js`）：

```js
class XxxAdapter extends BaseAdapter {
  async probe()            // → {available, version?, reason?}
  async run(opts)          // → {status, text, changedFiles, cost, raw}
}
```

| 类型 | 适用 | 现有成员 | 新增成本 |
|---|---|---|---|
| `generic`（配置驱动） | 命令 + 参数模板 + 权限参数这类标准 CLI | cursor / qoder / trae | **只改 members.json** |
| 专用适配器 | JSON 输出解析、REST、私有协议 | claude（JSON 解析）、doubao（REST） | 写一个约 150 行的类，注册一行 |

### promptMode：指令怎么进 CLI（这是踩过两次坑的地方）

| 值 | 指令怎么进 | argsTemplate 里放什么 | 什么时候用 |
|---|---|---|---|
| `stdin`（默认） | 写标准输入 | 什么都别放 | **首选**：最快，不受转义与换行影响 |
| `arg` | 当命令行参数 | `{prompt}` | 只在 CLI 明确不吃 stdin 时用 |
| `file` | 落成临时文件 | `{promptFile}` | CLI 只认文件（Trae 的 `--file`），或参数位被占用 |

> ⚠️ **多行指令绝不能走 `arg`。** 实测：双引号内的换行会被 `cmd.exe` 就地截断，
> 成员只收到第一行，**而退出码仍然是 0** —— 静默产出垃圾，
> 报告里却写着「3 / 3 成功」。这是本项目最危险的一类失败。

`file` 模式是本次为 Trae 新增的：把指令写进系统临时目录的一个临时文件，
命令行只传路径，执行完在 `finally` 里删掉。

## 三、豆包：没有 CLI，只能自写 REST 适配器

### 为什么不能用现成的

2026-09-29 实测推翻了原假设：

- npm 包 `@volcengine/arkclaw` 的 `package.json` 里 **`bin` 字段为空**，
  `description` 是 `"swagger client for @volcengine/arkclaw"` ——
  它是给开发者调用的 SDK 库，`npm i -g` 装完**敲不出任何命令**。
- 豆包没有官方 CLI。唯一可编程入口是火山方舟的 OpenAI 兼容端点。

### 端点

```
POST https://ark.cn-beijing.volces.com/api/v3/chat/completions
Authorization: Bearer $ARK_API_KEY
{"model":"doubao-seed-1-6-251015","messages":[{"role":"user","content":"Hello"}]}
```

响应是标准 OpenAI 结构：`choices[0].message.content` +
`usage.{prompt_tokens,completion_tokens}`。

### 两个刻意的设计（`src/adapters/doubao.js`）

1. **不估美元成本。** 豆包按人民币计价，塞进 `cost.usd` 字段会误导。
   只回报 token 数，成本交给上层按当期价目表算。
2. **`thinking` 字段默认不下发。** 它是方舟私有字段
   （`{"thinking":{"type":"disabled"}}`），老的 `doubao-pro` 系模型不认、发了会 400。
   需要时在 `members.json` 里显式加 `"thinking": "disabled"`。

### probe 会真发一次请求

带 `max_tokens: 1`。这是**唯一**能同时验证三件事的办法：

- API Key 有效（否则 401）
- **要用的模型已在方舟控制台开通**（否则 403/404）
- 端点可达

只 ping 端点挡不住"key 是对的、但模型没开通"这种最隐蔽的情况。

> **注意**：火山方舟的每个模型都要在控制台「开通管理」里**单独开通**，
> 不开通就是调不了。`members.json` 里的 `model` 是 Model ID，会随时间更新，
> 要按你实际开通的那个来填。

### ⚠️ 模型 ID 会退役，别照抄文档里的默认值

2026-09-29 实测踩到：从方舟文档抄来的 `doubao-seed-1-6-251015`，在平台上已经处于
**Retiring（正在退役）** 状态。

**方舟其实提供了列模型的接口，调一次就能拿到准确清单**：

```bash
curl -s -H "Authorization: Bearer $ARK_API_KEY" \
  https://ark.cn-beijing.volces.com/api/v3/models
```

实测返回 135 个模型，每个带 `status` 字段：

| status | 含义 | 怎么处理 |
|---|---|---|
| 字段缺失 | 在售（当前主力） | ✅ 优先选这些 |
| `Retiring` | 正在退役 | ⚠️ 别用，指不定哪天停掉 |
| `Shutdown` | 已下线 | ❌ 一定失败 |

### ⚠️ 404 有两种成因，方舟是分开说的 —— 千万别混为一谈

这是本次最有价值的一个发现：

| 服务端原文 | 真实原因 | 该做什么 |
|---|---|---|
| `Your account xxx has not activated the model yyy` | **Model ID 是对的**，只是账号没开通 | 去控制台「开通管理」点开通 |
| `The model or endpoint yyy does not exist` | **Model ID 名字不对** | 去核对准确的 Model ID |

如果翻译成同一句「模型不存在或未开通」，排查就会变成在
「换个 ID 试试」和「去控制台开通」之间反复瞎试。
`doubao.js` 的 `describeHttpError()` 已经把这两种情况**分开翻译**，并各给一条行动指引。

### ⚠️ 刚开通 ≠ 立刻可用：方舟的开通是「最终一致性」

2026-09-29 实测：在控制台点完「开通」之后，**同一分钟内** probe 一次返回 ✅ 可用、
下一次返回 ❌ `has not activated the model`。

而 `/api/v3/models` 里这个模型的元数据（1M 上下文、`version: latest-version`）**自始至终都在** ——
说明 Model ID 完全正确，纯粹是**节点间状态同步延迟**。
（那次的错误原文里账号名和模型名甚至被渲染成了 `%s`，连模板都没填完，侧面印证还在同步中。）

> **规训：遇到「刚开通却报未开通」，别去翻配置、别换 ID、别怀疑 key —— 重试几次就行。**
> 推论：这类调用在生产里值得加一层重试。

### 测试

`tests/doubao.test.mjs`，**22 条全通过**，全部用 mock fetch，离线可跑、不花钱。
覆盖重点是「没有 key 时不能崩」和「各类 HTTP 错误要翻译成人话且保留服务端原文」。

## 四、Trae：装得上，但坑在 Python 版本和它自己的打包

### 结论先说

`trae-agent` 是**唯一一个装起来需要特定 Python 版本的成员**。

### 坑 1：只有 GitHub 源码

PyPI 上 `trae-agent` / `trae-cli` **全部 404**。官方只有：

```
git clone https://github.com/bytedance/trae-agent.git
```

已 clone 到 `tools/trae-agent`（位置可控，没走会改系统 PATH 的安装脚本）。

### 坑 2：必须 Python 3.12，不能 3.13 ⚠️

`pyproject.toml` 里 `requires-python = ">=3.12"`，看着 3.13 也行。但依赖里钉死了：

```
tree-sitter-languages==1.10.2
```

这个包**只有 cp312 及以下的 wheel**，在 Python 3.13 上 pip 直接报：

```
ERROR: Could not find a version that satisfies the requirement
       tree-sitter-languages==1.10.2 (from trae-agent) (from versions: none)
```

本机托管 Python 是 **3.13.14**，所以第一次 `pip install` 整个失败。

**解法**：用 `uv` 单独建一个 3.12 环境（uv 能自己管理解释器）：

```bash
pip install uv                                        # uv 装进托管 venv
uv python install 3.12                                # 拉一个 CPython 3.12
uv venv --python 3.12 tools/trae-venv312              # 独立环境，不污染其他用途
uv pip install --python tools/trae-venv312/Scripts/python.exe ./tools/trae-agent
```

### 坑 3：trae-agent 漏了自己的依赖 ⚠️

装完之后 `trae-cli --help` **直接抛异常**，栽在两个包上：

```
ModuleNotFoundError: No module named 'docker'
ModuleNotFoundError: No module named 'pexpect'
```

原因：`docker` / `pexpect` / `unidiff` / `datasets` 被放在
`[project.optional-dependencies]` 的 **evaluation** 组里，
**但 `agent/docker_manager.py` 在顶层 `import docker`、`import pexpect`，
而 `base_agent.py` 又顶层 `import docker_manager`** ——
于是只装核心依赖时，连 `--help` 都打不开。

这是 **trae-agent 自己的打包疏漏**，不是配置问题。补装即可：

```bash
uv pip install --python tools/trae-venv312/Scripts/python.exe docker pexpect unidiff
```

（`datasets` 是评测用的重依赖，几百 MB，核心路径不需要，没装。）

### 坑 4：prompt 必须走 `--file`

CLI 的 task 是**位置参数**，但多行 prompt 经 `cmd.exe` 会就地截断（退出码仍 0）。
所以 `promptMode` 用 `file`：

```json
"promptMode": "file",
"argsTemplate": ["run", "--file", "{promptFile}"]
```

**另一个陷阱**：`-p` 是 `--provider` 的短选项，**不是 prompt**，别和别的成员混用。

### 配置

`tools/trae_config.yaml`（由 `env.TRAE_CONFIG_FILE` 指定）。
**密钥不落盘** —— trae-agent 的取值优先级是 `CLI > ENV > config`
（`utils/config.py` 的 `resolve_config_value`），
环境变量名 = `<provider 名转大写>_API_KEY`，所以配置文件保持零凭据、可安全提交。

默认配的是**豆包**（与 AgentHub 的 doubao 成员共用同一个 `ARK_API_KEY`，一处申请两处可用）；
想换任意 OpenAI 兼容端点（DeepSeek / OpenRouter / 本地 ollama），
改 `model_providers` 并把 `models.*.model_provider` 指过去即可，文件里已留好注释。

### L1 实测

```
trae-cli, version 0.1.0

show-config →
  Default Provider  doubao
  Model             doubao-seed-1-6-251015
  Max Steps         60
  API Key           Not set        ← 符合预期，走环境变量
```

> ⚠️ **"可用数"不等于"接入已完成"** —— 它取决于环境里有没有密钥。
> 写这份文档时豆包与 Trae 都真跑通了；但密钥只存在于当时那个 shell 进程里，
> 之后换个终端启动界面服务就会报「未设置 ARK_API_KEY」，**看起来像成员配错了**。
> 解法见下一节：密钥要落到 `.env`，不要靠 `export`。

### 规划者看得见的名单 = 引擎真能调动的名单

**这是被一次真实拆解暴露出来的问题。** 某次拆解，主脑把两个子任务都派给了豆包 ——
因为豆包在 `members.json` 里是 `enabled: true`，但当时它的密钥没设、根本跑不起来。
后果是**你先看到一份像模像样的计划，到执行阶段才挨个失败**。

原来 `planWithMember` 交给规划者的是「已启用」名单：

```js
const usable = registry.list().filter((a) => a.isEnabled)   // ❌ 含跑不起来的
```

现在改成先探活、只用实测可用的（探活走缓存，几乎不花时间；真探不到才退回宽松名单，
宁可多派几个人，也不要因为探活本身出问题而拆不出计划）：

```js
const probed = opts.probed || (await registry.probeAll())
const avail = usable.filter((a) => probed[a.id]?.available)
if (avail.length) usable = avail                            // ✅
```

修完再拆同一个目标，名单里就没有豆包了，派给了 claude / cursor / qoder。

> 一句话原则：**任何"让模型自己挑人"的地方，交给它的名单必须等于真实可用的集合。**
> 否则模型会非常认真地在一个空集合上做规划。

### 三层冒烟实测记录（2026-09-29 17:00）

| 成员 | L2 耗时 | 产出 | 用量 |
|---|---|---|---|
| 豆包 | 1269ms | `冒烟通过` | 59 in / 25 out tokens |
| Trae | 13605ms | `冒烟通过`（2 steps） | 6315 in / 276 out tokens |

> **一个环境变量管两个成员**：只设 `DOUBAO_API_KEY` 就够了 —— 豆包适配器兼容它，

> ⚠️ **别用 `ARK_API_KEY` 去喂 Trae**：它不认，而且报出来的是一段 Python 异常
> （堆栈里完全看不出是 key 的问题），极易误判成装坏了。

## 六、凭据怎么配（已闭环 ✅）

2026-09-29 已全部打通。**只需要一个环境变量**：

```bash
DOUBAO_API_KEY=<你的火山方舟 API Key>
```

两个前提，都在方舟控制台：

1. **创建 API Key** —— 「API Key 管理」→ 创建，**在创建弹窗里立即复制**
   （它是 UUID 形式，不是列表里显示的那串名字）。
   如果已经建过，点该行右侧的「**查看**」图标复制完整值。
2. **开通模型** —— 「开通管理」里点开通。注意**每个模型要单独开通**，
   而且**开通后有几同步延迟**（见上文，重试即可）。

### ⚠️ 别用 `export`，用 `.env`

**这一条是被坑出来的。** `ui/server.js` 是**长驻进程**：

```bash
DOUBAO_API_KEY=xxx node tests/smoke-member.mjs doubao   # ✅ 能通（同一个 shell 的进程）
DOUBAO_API_KEY=xxx node ui/server.js                    # ✅ 也能通
# 换个终端再 node ui/server.js                          # ❌ 报「未设置 ARK_API_KEY」
```

界面上表现为豆包那一行红着、写着缺密钥 —— 而配置文件和适配器其实都是好的，
排查方向完全被带偏。**密钥要落到磁盘上的 `.env`**：

```bash
cp .env.example .env      # 然后填 DOUBAO_API_KEY=...
node ui/server.js         # 启动时会打印「已从 .env 载入 N 个环境变量」
```

规则（`ui/server.js` 的 `loadDotEnv`）：一行一条 `KEY=VALUE`，`#` 开头是注释，
**已经存在的进程环境变量优先**（不会被 `.env` 覆盖），文件不存在就静默跳过。
`.env` 已在 `.gitignore` 里。

验证（一条命令跑完 L1/L2/L3）：

```bash
node tests/smoke-member.mjs doubao      # 有 .env 时不用再带前缀
node tests/smoke-member.mjs trae
```

## 七、拆解失败最隐蔽的一种：模型输出被截断 ⚠️

**现象**：点「拆解」，等三十多秒，界面弹「没拆出可用的计划」。

**为什么难查**（两层叠加）：

1. `extractJson` 要求代码围栏**成对**（开头 ` ```json ` 与结尾 ` ``` `）。
   输出被截断时**结尾那个围栏压根没吐出来** → 围栏匹配失败 → 退化成
   "全文里第一个 `{` 到最后一个 `}`" → JSON 不完整 → `parse` 抛错 → 返回 `null`。
2. `apiPlan` 返回诊断信息时写的是 `String(raw || '').slice(0, 2000)` ——
   **正好把"输出被截断"这个最关键的信息自己切掉了**。截图里 `raw` 长度精确等于 2000，
   一度误判成"模型被 max tokens 限制了"。真因在自己这行代码里。

**怎么定位的**：绕开界面直探一次（同样的 `buildPlannerPrompt` + 同一个成员），
拿到 **5034 字符、围栏成对、`extractJson` 成功** —— 说明那次界面失败不是模型输出坏了。
（直探那次恰好没触发截断，两次调用输出长度不同，这类失败是**偶发**的。）

**修法（两处）**：

1. `extractJsonLoose(text, { minArrayField, minItems })` —— 抢救式解析，四级递进：
   - 先走严格版；
   - 失败则找「**最后一个完整闭合的数组元素**」，截到那里补上 `]}`，**保住前面已写好的子任务**；
   - 再不行就按括号栈补齐（处理截在字符串中间 / 截在键名后的情形）；
   - 还不行就从尾部逐个回退，最多 20 段。
   - 关键约束：**形状校验**。抢救出来的对象必须含非空 `subtasks`，否则宁可返回 `null` ——
     不能因为"能 parse"就交出一份没有子任务的假计划。
2. `apiPlan` 不再截断 `raw`，并额外返回 `rawLength` / `repaired` / `repairReason`。
   界面在 `repaired` 为真时于计划表上方挂一条黄色警告。

**为什么必须显式警告，不能静默抢救**：抢救出来的计划少了一两个子任务，
用户会以为"计划本来就这么短"。**少掉的那部分活没人干，比直接报错更危险。**

测试：`tests/planner.test.mjs` 有 10 条针对它的用例，夹具就是这次真实的失败形态
（截断在第二个子任务中途、结尾围栏缺失）。反证做过：把抢救逻辑短路掉，
这 10 条里有 5 条立刻变红，而原有 15 条严格版断言全绿。

**顺带一条通用教训**：**诊断信息的截断上限会把人带偏**。
凡是"把原始输出返回给调用方/展示给用户"的地方，长度上限要么不给，
要么**把真实长度一并返回**。否则你永远在分析一份被自己裁剪过的证据。

### 第二轮又补了两条：抢救"成功"反而更危险

**1. 形状校验必须下探到元素级。**

只检查「`subtasks` 数组非空」是不够的。第二轮救出一个「有 3 个子任务」的 JSON，
但第三个只剩 `{id, title, memberId, role}` —— **没有 prompt**。
引擎 `validatePlan` 会拒，界面却照常渲染、照常放行「确认执行」，
点下去才弹「子任务 s3 缺少 prompt」。用户白点一次，且看不出哪一行缺。

现在规则是：**抢救的产物必须能通过引擎校验，否则不算抢救成功**（宁可说"没拆出来"）。
并且**严格版也要过同一套校验** —— "JSON 语法合法"不等于"计划可用"。

界面侧补了第二道防线：残缺行标 `data-broken`、指令框默认展开、行内有红字说明，
点「确认执行」在本地就被拦下并点名是哪几行（不打服务端那次往返）。
`ui-smoke.mjs` 第 7b 节有 6 条断言钉住它（`/api/plan` 与 `/api/run` 都打桩，零成本）。

**2. 从源头降低截断概率 —— 这一条比上面的抢救更值钱。**

`buildPlannerPrompt` 里加了一条硬要求：

> 每个子任务的 prompt 控制在 150 字以内，只写「做什么 + 交付什么 + 关键约束」，
> 不要复述总目标、不要铺陈背景、不要罗列长长的检查清单。

实测对比（同一目标）：

| | 原始输出 | 单个指令长度 | 结果 |
|---|---|---|---|
| 改动前 | 4713 / 3920 字符 | 1498 / 1092 / 973 / **0** | 两次都**截断** |
| 改动后 | **1281 字符** | 157 / 141 / 115 / 110 | **完整** |

而且计划质量没有下降（依赖链、成员分配、最终交付都齐）。

**教训：与其把"截断之后怎么救"做得很精巧，不如先让它别被截断。**
抢救逻辑是兜底，不该是主路径。

### 2026-10-02 补充：这两条上限现在跟着规划者走

上面那两条（子任务 2-6 个、prompt ≤150 字）是**为截断这件事**加的，

## 八、★★ 探活假绿：`--version` 通过 ≠ 这成员能干活

**现象**（真跑协同任务时踩到）：界面上 Trae 是绿的，规划者也放心把活派给了它；
执行到第 3 秒就炸，产出只剩一段 Python 堆栈：

```
openai.OpenAIError: Missing credentials. Please pass an `api_key`,
`workload_identity`, `admin_api_key`, or set the `OPENAI_API_KEY` ...
```

**根因**：Trae 的探活走的是 `trae-cli --version` —— **这条命令根本不碰 API Key**，
所以永远返回成功。真正需要密钥的是 `run` 子命令。

**为什么这很危险**：它把「配置缺失」伪装成了「运行期故障」。探活这一层的全部意义
就是把问题拦在**花钱之前**；假绿等于这层白做。更糟的是**规划者会据此把活派过去**
（见 §5 那次同类问题 —— 但那次是靠"探活缓存预热"绕的，治不了根：
只要探活本身不准，预热也只是把错的结论缓存起来）。

**修法**：成员配置声明 `requiredEnv`，探活前先查环境变量：

```json
{ "id": "trae", "enabled": true, "requiredEnv": ["DOUBAO_API_KEY"] }
```

`MemberRegistry` 里统一前置检查（`precheckEnv`，`probeAll` / `probeOne` 共用），
缺了就直接判不可用并说明缺哪个。修完的效果：

```
❌ 不可用 trae · 缺少环境变量 DOUBAO_API_KEY（配置里声明了 requiredEnv，探活前先查）
```

**边界（别指望它包治百病）**：这只挡「没配」，挡不住「配错了」——
key 拼错、模型没开通、额度用尽、登录态过期，它统统看不出来。
所以能用真实调用的成员（豆包 REST 走 `max_tokens: 1` 真调一次）**仍然要真去调**，两者互补。

**通用教训**：**探活要测的是「能不能干活」，不是「命令在不在」。**
凡是重活依赖某个前置条件的成员（密钥 / 登录态 / 模型开通 / 目录受信），
要么想办法让探活碰到那个前置条件，要么就显式把这些条件检查出来。

## 九、⚠️ 引擎侧的失败策略：一个子任务失败会停掉整个任务（已闭环 ✅ → 见第十五节）

这一条不属于"成员接入"，但它是在同一次实跑里暴露的，且直接决定"钱花得值不值"，所以记在这里。

> 布尔换成了三个有语义的策略（默认 `skip-blocked`）、引入第三种状态 `skipped` 并四层贯通、
> 以及把"缺口"明确写进下游的指令和报告（`salvage` 策略的安全带）。

## 十、真跑之后改掉的两处「上游信号被丢掉」（已闭环 ✅）

第三轮真跑拿到了一份交付（`.agenthub/real-run/outputs-run3/s3-claude.md`），
里面点出了两处**引擎自己把上游信号扔掉**的地方。两处都已修，且都补了测试与反证。

### 10.1 `is_error`：退出码 0 ≠ 这活干成了

`claude --output-format json` 在「达到最大轮次」「API 错误」这些情况下
**仍然可能以退出码 0 结束**，真实信号只存在于 payload 里：

```json
{"type":"result","subtype":"error_max_turns","is_error":true,"result":"已达到最大轮次"}
{"type":"error","error":{"type":"api_error","message":"Internal server error"}}
```

原来只看 `exitCode` → 记成 `status:'ok'` → 判定层因为 `status==='ok'` 继续往下判 →
而"已达到最大轮次"不含任何现有词 → 最终判 ok。**一层保护整条漏掉。**

现在 `src/adapters/claude.js` 里把判定抽成纯函数 `isErrorPayload(payload)`，
`is_error` 优先于退出码。抽成纯函数是为了能**直接测** ——
mock 子进程代价太高，结果往往是干脆不测，而这段恰恰是最容易漏一种形态的地方。

### 10.2 `permission_denials`：唯一能识别那次假成功的证据，之前从没被读过

第三轮之前的某次运行报「3 / 3 成功 · 0 失败」，而三个成员的产出全是
「测试文件已写好，但命令被 `This command requires approval` 拦住、没真正执行」。
那次运行留下的证据在 `.agenthub/runs/run-1790658473692.json`：

| 子任务 | 产出长度 | `permission_denials` | `is_error` |
|---|---|---|---|
| s1 | 1027 字符 | **8 条** | false |
| s2 | 587 字符 | **5 条** | false |
| s3 | 475 字符 | 0 条 | false |

**为什么加正则也没用**：三条产出是 1027 / 587 / 475 字符，**全部超过环境词的 400 长度门**，
即便把 `requires approval` 补进 `ENV_ERROR_PATTERNS` 也不会采信。
`is_error` 又全是 false，救不了。

所以 `quality.js` 加了一条**不依赖文本长度**的规则：`permission_denials` 非空
**且**产出自称未真正执行 → `suspect / not-executed`。
这是「产出有效性判定」从"猜文本"迈向"看证据"的第一步 ——
**文本会撒谎，被拦下的命令列表不会。**

> 证据文件所在目录 `.agenthub/runs/` 被 `.gitignore` 忽略（它确实是运行产物），
> 所以关键样本已抽成夹具 `tests/fixtures/run-permission-denials.json` 进版本库。
> 顺带修掉一个假绿：原来夹具不在时那一组断言会**静默跳过并以 exit 0 收场**，
> 现在夹具缺失 = **硬失败**。

## 十一、★★ 一个恒为空的字段：`changedFiles` —— 上游评审差点据此写出恒定误报的规则

这是本次闭环里**最值钱的一条**，因为它是一次"**AI 给出的建议本身错了**"的完整案例。

上游两份评审（`s2-qoder.md`、`s3-claude.md`）都把这条列为"真缺口"：

> **G7 声称改动但零改动** —— 文本 `已修复全部问题`，而 `changedFiles: []`。
> 建议规则：`judgeOutput(r.text, { status, changedFiles })`；
> 文本命中完成语 且 `changedFiles.length === 0` 且权限档非只读 → 标 `claimed-edit-no-change`。

写法本身没错，**错在没有人去核实这个字段到底有没有被填过**。核实结果：

```
.agenthub/runs/*.json 全部 13 个条目 → changedFiles 非空 = 0 / 13
```

因为三个适配器（claude / generic / doubao）**全都硬编码返回空数组**，
`changedFiles` 是一个**声明在接口里、一路传到报告、却从来没有人填过**的死字段。

照那个建议实现，这条规则会在**每一次写档运行**上误报（只要正文出现"已修改"）——
而"一个会喊狼来了的标记，比没有标记更糟"正是 `quality.js` 开头写下的原则。

### 怎么修的

**把「没采集」和「采集了但为空」分开**，而不是直接照抄：

| 取值 | 含义 | 判定 |
|---|---|---|
| `null` / `undefined` | **未采集**（当前三个适配器都是） | 不判（宁漏勿误） |
| `[]` | 确实采集过，没有改动 | 写档 + 完成语 → `suspect` |

三处协同改动：

1. **适配器**：`changedFiles: []` → `changedFiles: null`（3 个文件）
2. **`orchestrator.js`**：`r.changedFiles || []` → `r.changedFiles ?? null`
   —— 这个 `||` 就是陷阱的成因，它把"没数据"伪装成"没有改动"
3. **`quality.js`**：规则加一道安全带 `Array.isArray(cf) && cf.length === 0`

> 因此这条规则**目前不会触发** —— 这是诚实的现状：这个缺口现在还识别不了，
> 因为还没采集数据。等哪天真的实现了文件改动采集，它会自动开始工作。

### 复盘：这次是"三步"而不是"一步"

1. 上游 agent 给出建议（**看起来有依据**：确实引用了 `orchestrator.js:189` 写入了该字段）
2. **去核实前提**（读全部真实运行数据 → 13/13 为空）
3. 按核实结果修，并把区别写进测试

第 2 步是纯人工的、也是唯一能拦住这个错的。上游评审引用行号证明"字段被写入了 entry"，
但"被写入"≠"有值" —— **引用了代码位置，不等于验证了数据的实际取值。**

## 十三、第二轮：文件改动采集 —— 让 `claimed-edit-no-change` 真正生效

上一节留了个尾巴：规则写好了、测试也绿了，但**它永远不会触发** ——
因为 `changedFiles` 没有任何实现去填。规则是死的。

这一轮把它接活：新增 `src/engine/changes.js`，由**引擎自己**采集文件改动。

### 采集方式：跑前跑后各拍一次快照，然后 diff

逐文件记 `mtime : ctime : size`，两次快照一比就得到 added / modified / removed。
**不读文件内容** —— 在几万文件的项目上做全量哈希是不可接受的，而 mtime+size
对"agent 刚写了文件"足够灵敏（新文件必然命中 `added`）。

为什么还要带上 `ctime`：`mtime + size` 会漏掉**同尺寸覆盖写**（改一个字符、长度不变）。
`ctime` 在内容变动时一定会更新，正好兜住这种情况 —— 有专门的断言钉住它。

### ★ 两条铁律：宁可说"不知道"，也不给错答案

这个模块的产物**直接用来给成员定罪**，所以：

**1. 采不全就返回 `null`（未采集），绝不返回 `[]`。**

超时、超文件数上限、工作目录读不到 —— 一律 `null`。因为这两种值在判定层**含义相反**：

| 返回值 | 含义 | 判定层 |
|---|---|---|
| `null` | 我没看完（或根本没看） | 不判 —— 拿没数据定罪就是误报 |
| `[]` | 我完整看过，一个文件都没变 | 写档 + 声称改了 → **判可疑** |

一旦让"采不全"退化 `[]`，这条规则立刻变成恒定误报。
**这里有个特别容易踩的子坑：工作目录读不到，会被误当成"空目录"。**
空目录 diff 出来是 `[]` —— 于是"读不到"被伪装成了"零改动"。
所以根目录 `readdir` 失败也必须标记 `truncated`，有专门的断言（反证 6）。

**2. 快照必须有上界。**

本仓库 `tools/` 一个目录就有 **8498 个文件**（trae 的 Python venv + cursor agent），
真实项目的 `node_modules` 动辄十万。没有上界 = 每个子任务都要卡几十秒。

所以有三重闸：`maxFiles`（2 万）、`maxMs`（3 秒）、`maxDepth`，
加一份忽略名单（`node_modules` / `.git` / `__pycache__` / 各类构建产物，
以及**名字里带 `venv` 的一律跳过** —— 虚拟环境目录名千奇百怪，
`trae-venv312` 这种精确匹配是挡不住的）。

### 只在写权限档采集

`readonly` / `plan` 档本就改不了文件，采了是白花时间，所以不采（结果就是 `null` = 未采集）。
判定规则同样只在写档生效 —— 两边共用**同一份** `WRITE_PERMISSIONS` 定义（从 `quality.js` 导出），
避免"采了但判定不认"。

### 三态贯通：引擎 → 报告 → 界面

数据采出来还得让人看见，而**"未采集"和"零改动"在每一层都不能混**：

| 层 | 有改动 | 完整采集、零改动 | 未采集 |
|---|---|---|---|
| 报告（`trace.js`） | `改动文件（2）：src/a.js、tests/b.mjs` | `改动文件：**无**（已完整采集）` | `改动文件：未采集（…）` |
| 界面（卡片） | `改动 2 个文件：src/a.js、…` | `改动文件：无（已完整采集）` | `改动文件：未采集` |

报告层如果一律写"无改动"，就是把"我没看"说成"我看过了、没有" ——
和 `changes.js` 防的是同一个错，只是搬到了给人看的那一层。

### 反证（本轮 3 轮，共 5 条断言）

| # | 拆掉什么 | 变红 | 证明了 |
|---|---|---|---|
| 5 | 采不全时返回 `[]` 而不是 `null` | 2 条（模块 + 编排层各一） | 链条会把"没数据"传成"零改动" |
| 6 | 工作目录读不到时不标记 `truncated` | 2 条 | "读不到"会被伪装成"空目录 → 零改动" |
| 7 | 界面把"未采集"渲染成"无改动" | 1 条（界面冒烟） | 误导会从数据层长到 UI 层 |

## 十四、第三轮：两个「数字在说谎」（已闭环 ✅）

### 14.1 ★★ `qoder` 的花费一直是 `$0.0000` —— 0 被当成了测量值

**症状**：报告里 qoder 那条恒显示 `$0.0000`。看起来像"这次很省"，实际是**没读到数据**。

**查法**：翻了 33MB 的 qodercli bundle，确认它 `-o json` 的返回结构和 claude 同构，里面有 `total_cost_usd`、`total_credits`、`permission_denials`。

**实测一次真调用**（约 0.16 积分），拿到的原文是：

```json
{ "total_cost_usd": 0, "total_credits": 0.157647882,
  "usage": { "input_tokens": 0, "output_tokens": 0 },
  "context_usage_ratio": 0.095, "permission_denials": [] }
```

三个信号全部被丢掉或误读：

| 字段 | 实际值 | 之前怎么处理的 | 后果 |
|---|---|---|---|
| `total_cost_usd` | `0`（**硬编码**，不是真值） | 原样当成本 | 报告印 `$0.0000` |
| `total_credits` | `0.157647882`（**真值在这**） | **从没读过** | 真实花费彻底不可见 |
| `usage.*_tokens` | 全 `0` | 原样求和 | Token 栏显示 0 |

**两条口径是并列的，不折算。** `usd` 和 `credits` 是两种计价单位，汇率/单价不该由引擎编。豆包适配器早就这么做（"按人民币计价，塞进 usd 会误导"），generic 只是落后了。

**修法**（`src/adapters/generic.js`）：

```js
// 0 不是测量值 —— 只有 > 0 才当成"读到了"
export function positiveNumber(v) {
  return typeof v === 'number' && v > 0 ? v : undefined
}
```

`parsePayload` 变成纯函数导出（**为了能拿真实样本直接测，不必 spawn 子进程花钱**），只把正数写进 `cost`，`total_credits` 单独读进 `cost.credits`。

**三态贯通**（引擎 → 报告 → 界面）：

| 状态 | 报告里显示什么 |
|---|---|
| 有美元成本 | `$0.0123` |
| 只有积分 | `0.157648 积分` + 一行"该成员按积分计费，CLI 不返回美元成本" |
| 什么都没有 | `未知` |

关键点：**总数后面会自动加注**，只在并非所有子任务都上报时才出现，例如
"合计 $0.65（另有 3 个子任务未上报美元成本、不在此数内）"。全部报齐时**不加任何注解**（有专门的反证测试钉这一条，防止注脚变成噪音）。

配置侧：qoder 从 `outputFormat: text` 改成 `json`，补上 `textPath: "result"` / `costPath: "total_cost_usd"` / `creditsPath: "total_credits"` / `billing: "credits"`。

> 顺带查了 cursor 和 trae：cursor 支持 `--output-format json`，但**返回里既没有 cost 也没有 `permission_denials`**（只有内部 protobuf 的 `is_error`）→ **不照抄，保持 text**。trae 根本不支持。**能开出 JSON 不等于能拿到想要的那几个字段。**

### 14.2 ★★ `free` 是个假标签 —— 它还会影响派活

查 14.1 的时候顺手发现：多个成员挂了 `free` 能力标签。而 qoder 实测**每次调用都扣积分**。

这条标签的危害不止是"界面显示不实"——它长在一条决策链上：

```
成员挂 free 标签 → capabilities 进规划者提示词（planner.js 的 roster） 
→ 规划者"为省钱"优先把活派给它 → 第三轮那个 6.5 分钟的子任务很可能就是这么来的
```

**修法**：

1. 清掉所有 `free` 标签（3 处 pattern，共 5 处出现）
2. 给 6 个成员加**如实的** `billing` 字段：claude/cursor = `subscription`、qoder = `credits`、trae/doubao = `tokens`、dsh = `unknown`
3. `planner.js` 新增 `BILLING_LABEL` 映射（**刻意不写"免费"二字**），roster 每行追加 ` · 计费 [订阅内，调用不单独计费]`
4. 拆解要求新增第 8 条，把话说明白：

> "「计费」只说明**怎么扣费**，不代表便宜或贵。**不要**因为某项看起来"不单独计费"就把活优先派给它 —— 选人看能力匹配，不看计费口径。"

5. **透到界面**：`ui/server.js` 的 `apiMembers` 是白名单字段，之前界面拿不到 `billing`；现已透出，成员管理弹窗、新建会话选择框、成员笔记弹窗三处都显示计费口径。添加成员弹窗的能力标签默认值也从 `code,free` 改成 `code`，并加了一句提示："能力标签只描述能干什么，不要写 free/免费 —— 它会被规划者读到并影响派活。"

> **一个字段"被写进 entry" ≠ "它真的有值"。** 上一轮 `changedFiles` 恒为空是这个陷阱，这一轮 `total_cost_usd` 恒为 0 也是这个陷阱，只是穿了不同的马甲。

### 14.3 反证（本轮 3 轮）

| # | 拆掉什么 | 变红 |
|---|---|---|
| 8 | `positiveNumber` 把 `0` 当测量值 | 2 条 ★★ |
| 9 | `costCell` 退回 `$0.0000` | 3 条 |
| 10 | `credits` 读错字段 | 1 条 ★★ |
| 11 | 成员行不显示计费口径 | 1 条（界面冒烟） |
| 12 | `billingLabel` 兜底返回 `free` | 1 条（界面冒烟）★ |

### 14.4 遗留（未修，说清楚）

- **预算闸对积分计费成员是瞎的**：`orchestrator.js` 里 `spentUsd += r.cost?.usd || 0`，全程 qoder 的任务 `spentUsd` 恒 0、预算永远触发不了。已加 `unknownCostCount` 计数并在中止文案里如实说明"另有 N 个子任务未上报美元成本、不在此数内"，**但根治需要单价表**（每个成员 1 积分 = 多少美元），这个数我们不该编，得用户填。

## 十五、第四轮：失败策略（第九节那笔账，终于还了 ✅）

第九节记下的是这一整条链里**最贵**的一个问题：一个子任务失败 → 整单停掉 → 最终交付永不执行 → 已经花掉的钱只换到中间产物。这一节是它的收口。

### 15.1 把布尔换成三个有语义的策略

原来的开关是 `stopOnFailure: true/false`。一个布尔装不下这里真正要做出的判断，因为"剩下的活怎么办"至少有三种合理意图：

| 策略 | 谁被跳过 | 代价 / 收益 |
|---|---|---|
| `abort` | 失败之后的**所有**步骤（含不相关的旁支） | 最省后续开销，但已花的可能白花 —— **就是当年翻车的那个** |
| `skip-blocked`（**默认**） | **只跳过依赖断链的**那几条 | 不依赖失败结果的旁支照跑完；不浪费，也不硬凑 |
| `salvage` | 一条都不跳 | 最终交付照样跑；代价是它**带着缺口**，所以必须把缺口说出来 |

为什么默认不是 `salvage`：它会产出"输入少了一块"的成品，而**下游成员不一定会如实地把这件事写进结论**。默认取"不浪费也不说谎"的中间那条；真想要那份成品，用户在计划确认框里点一下就切过去。

为什么默认不是 `abort`：它把不相干的旁支也一起停掉 —— 那些步骤的前提根本没被破坏。

旧字段仍兼容：`stopOnFailure: true` → `abort`，`false` → `salvage`。**这里有一处行为变化**：旧代码在 `false` 时是"带洞**静默**继续"（依赖缺失时那段上游在 prompt 里凭空消失、下游根本不知道自己少了一份输入），映射到 `salvage` 后缺口会被明说。

### 15.2 ★ 第三种状态：`skipped`（引擎没有调用成员）

这一轮真正的核心不是"多一个选项"，而是**承认第三种状态的存在**。

```
ok        —— 调用了成员，进程正常退出
failed    —— 调用了成员，但没干成
skipped   —— **压根没调用成员**：依赖断链 / 策略中止 / 预算上限
```

判定口径统一成一句：**`skipped` = 引擎没有调用成员，所以它没花钱、也没产出。**

三种"没执行"都归到这里，并且用 `skipKind` 分开存（`blocked` / `aborted` / `budget`）—— 因为处置方式不同：失败要看产出、要考虑重试；没执行只需要看策略和预算，重试没用。分类按**直接原因**而不是追根因（预算为 0 时第 1 层直接撞闸记 `budget`，第 2 层因依赖被跳过记 `blocked`），这样顺着每条记录的原因逐条查上去就能追到根因，比一律标成同一个词更可查。

> 第五轮又往这个枚举里加了第四种 `user`（用户主动放弃）。它的语义跟前三种**不是一类** —— 前三种是"引擎判定不能跑"，只有它是"人拍板不要了"。见 16.2。

这个状态一路贯通，每一层单独钉了一遍：

| 层 | 修之前 | 修之后 |
|---|---|---|
| 编排层 `orchestrator.js` | 失败即 `break`，**后面几条连一条轨迹都没有** | 每条都留一格；每种策略下 `轨迹条数 === 计划条数` |
| 轨迹层 `trace.js` | `failedCount = status !== 'ok'` → 把"没执行"算成"失败" | `executedCount` / `failedCount` / `skippedCount`(+按类) / `degradedCount` 分开数 |
| 报告层 `toMarkdown` | 表格印 `failed`；成本分母把 skipped 算进去 | 印「未执行」；成本分母改成"实际执行过的条数" |
| 界面层 `app.js` | （原来根本没有这个状态） | 灰底虚线卡片，**明确不用红色** —— 红卡片会让人去点重试 |

一个具体的例子说明为什么分母也要改：若 5 条计划里 1 条未执行、4 条都没上报成本，旧的 `costUnknownCount` 会说"另有 **5** 个子任务未上报成本"，而正确答案是 4 —— 那道注脚自己也在说谎。

### 15.3 ★★ 静默消失：控制流上的同一个错

第九节那次翻车的直接机制是 `break`。它的后果不止"少跑了几个"：

- 报告里那几条**整段消失** → 用户以为计划本来就只有 3 步
- 中止事件只说"按策略停止后续执行" → 不知道跳了谁，也不知道还剩什么是能用的

所以补了收尾：`for (const st of plan.subtasks) if (!ctx.results[st.id]) markSkipped(...)`。**这是和 `changes.js` / `quality.js` / `trace.js` 里修的一模一样的错，只不过发生在编排层的控制流上。**

### 15.4 ★★ 缺口必须同时写进 prompt 和报告

`salvage` 让下游带着缺口跑，于是有了一个新的说谎机会：**下游不知道自己少了输入，交出一份看起来完整、实则少了一块的结果。**

两处都堵：

1. **给下游的指令**（`buildPrompt`）。旧写法是 `if (!up) continue` —— 那段上游凭空消失。现在改成单独一段：

```
【⚠️ 上游有缺口，你的结论必须带上这个前提】
- 子任务 s3：**执行失败** —— 成员 b 执行失败：模拟的失败原因
上面这些子任务没有给你可用输入。请在缺它们的情况下尽力完成本次任务，
并在结论开头用一句话写明：缺了哪一项、因此哪些结论不完整或未经核实。
**不要假装它们的结果存在。**
```

判定"有没有可用产出"的标准是严格的 `status === 'ok'`：真实 entry 一定带 status，所以**没有 status 也按缺口处理** —— 宁可对下游多说一句，也不放一个状态不明的上游混进上下文。（这条改动让 8 个测试夹具必须补上 `status: 'ok'`，那是对的：真实 entry 一定有，夹具也该有。）

2. **报告**。带缺口跑完的条目自己可能是 `ok`，所以多记一维 `degradedUpstream`，表格印 `ok ⚠️缺口`，详情里写明缺的是谁 —— **一条"在上游缺失下硬跑出来的结论"，不能和"输入齐备的结论"在报告里长得一模一样。**

### 15.5 顺手发现的第三处 `$0` 谎：总数那一格

生成报告样本肉眼过的时候才看见的：上一轮把**单格**的 `$0.0000` 改成了"未知"，但**总数**那一格是直接 `$${totalCostUsd}`，而"零个上报"时它就是 `0` —— 于是汇总行印出 `花费 $0`，等于宣称"这次免费"。

同一个谎从格子搬到了汇总行。现在分成四种情况：

| 情况 | 印什么 |
|---|---|
| 有人报了 | `$0.65（⚠️ 另有 N 个未上报成本…）` |
| 只有积分 | `未折算成美元（N 个子任务按积分计费，合计 x 积分）` |
| 谁都没报、但确实跑过 | `未知（N 个实际执行的子任务都没有上报成本）` |
| 一条都没执行 | `无（没有任何子任务被执行）` ← 这是**已知的零**，可以印 |

### 15.6 反证（本轮 3 轮，其中一轮白做）

| # | 拆掉什么 | 变红 |
|---|---|---|
| 13 | `failedCount` 退回 `status !== 'ok'` | **5 条** ★★ |
| 14 | 收尾记录整个拿掉（就是当年那个 `break`） | 2 条 ★★ |
| 15 | 缺口不再告知下游（退回静默略过） | **6 条** ★★ |
| 16 | 界面上未执行不再走短渲染 | 2 条（界面冒烟） |
| 17 | 界面上"未执行"并进普通渲染 | 3 条（界面冒烟）★ |

> ⚠️ 反证 17 的**第一版白做了**：我只把 `cls`/`statusText` 的映射改成 `fail`，结果全绿。
> 原因是未执行的卡片走的是**独立分支**，压根没读那两个映射 —— 变异点没打在要害上。
> 补上"并进普通渲染"这一步才变红。**变异测试自己也会说谎：全绿不代表断言承重，可能是这次改的代码根本没被跑到。**

## 十六、第五轮：单卡片「重试 / 换人 / 跳过」

前三轮修的是**读数据时的谎**，第四轮修的是**失败之后怎么走**。这一轮修的是另一件事：**一次运行里有一步没好，怎么只补那一步。**

原来的答案只有一个 —— 整单重跑。于是"重试一次"这件事的代价是"把已经成功的四步再花一遍钱"。这一轮把它拆开。

### 16.1 ★★ 花钱的边界（`needsRun`）

这个功能里最要紧的不是按钮，是**哪些活允许被重跑**。一句话：

> **已 `ok` 的绝不重跑；已 `failed` 的只重跑用户点名那一个；被 `skipped` 的重新评估（免费）；被用户跳过的，续跑不许替他把这一步翻案。**

四条各自的理由：

| 状态 | 跑不跑 | 为什么 |
|---|---|---|
| `ok` | **不跑** | 整单重跑一次要多花一遍钱，而重试存在的理由恰恰是"别重复花已经花过的钱" |
| `failed` | 只跑**点名的那个** | 重做一件失败过的活是一笔新开销，必须是人的明确决定，不能"顺便"发生 |
| `skipped` | 跑（重新评估） | 它一分钱没花过，重评估是免费的 —— 而卡住它的那一步修好后，这些步骤**应该自己跑起来**，这正是重试的收益 |
| `skipped` + `user` | **不跑** | 那是人的最终决定 |

预算上的推论：`resume` 的开销 ≈ 这次真正要重跑的那几步，**不是**全程重跑一遍。

### 16.2 ★ 用户跳过 ≠ 被策略跳过

第四轮只有一种"没执行"，这一轮它裂成两种，因为**语义不同**：

```
skipped / blocked   —— 引擎判定它不能跑（前置坏了）
skipped / user      —— 用户拍板：这一步的产出不要了
```

差别在**下游怎么看它**：用户说"不要了"，意思就是**它不再是下游的必须前提**。所以依赖它的步骤不该继续被它卡住，而应该**带着"缺了它"的标记继续跑**。

于是断链判据也拆成两个：

```js
brokenDeps(st, ctx)    // 所有没有可用产出的上游（含 user-skip）
blockingDeps(st, ctx)  // = brokenDeps 减去 user-skip —— 只有这些才"卡住下游"
```

- `advance()` 里决定"跳不跳这一条"用 **`blockingDeps`**（用户已放弃的不算卡）
- 记 `degradedUpstream`（这条产出是不是在残局下跑出来的）用 **`brokenDeps`**（用户放弃的**也是**缺口，必须标出来）

同一个词在两处取不同的值，看着像笔误，其实是这一轮最容易写错的地方 —— 反证 20 就是专门钉它的。

### 16.3 `advance()`：首跑与续跑共用一份逻辑

`run()`（整单首跑）和 `resume()`（接着跑）现在共用同一个 `advance(plan, ctx, trace, onEvent, { reason, onlyId })`。

分两份写迟早会漂移，这个仓库已经踩过一次：`WRITE_PERMISSIONS` 定义在两处，结果"采集了但判定不认"。所以这里从一开始就只留一份，`reason` 只影响事件文案和"谁该重跑"的判定。

### 16.4 ★★ 现场（ctx + trace）：丢了必须明说

单卡片重跑需要**引擎的现场** —— `ctx.results` 里存着 `raw` / `prompt` / `spentUsd` / `changedFiles`（`null` 与 `[]` 的区别就在这里）。前端手里的 `task.cards` 字段不全，拼不回来；硬拼等于把引擎内部结构复制一份到浏览器，两边迟早不一致。

所以服务端加了 `RUNS`（`taskId → { plan, ctx, trace, options, workdir }`，只留最近 20 次，本地单用户工具不需要持久化）。

**关键在于找不到现场时怎么办。** 这里有一条必须守住的线：

> 绝不能退化成"那就把整个计划重新跑一遍吧"。
> 用户点一次重试，就被多扣一遍全程的钱 —— **比没有这个功能更糟。**

现在如实报错并让他自己决定：

```
找不到这次运行的现场（服务可能重启过）—— 不会替你重跑整单，请重新执行整个计划
```

### 16.5 `upsert`：重跑不许在报告里留下两条记录

重跑的同一个子任务会**第二次**写轨迹。原来 `trace.add` 是纯追加 → 报告里同一步出现两条、统计把它算成两个子任务、`轨迹条数 === 计划条数` 这条横切保证当场失效。

新增 `Trace.upsert(entry)`：同 id 就地覆盖（保留原 `index`），首跑时退化成新增 —— **首跑与续跑因此共用同一条写入路径**。文件里三处 `trace.add` 全部换成 `upsert`。

### 16.6 界面

- 卡片上的三个按钮：**重试 / 换人 / 跳过**。未执行的卡片也给（重试同样是对它的正确处置）。
- **换人弹窗**只列**实测可用**且非当前成员的成员 —— 让人选了再报"该成员不可用"是白费一次操作。
- **跳过弹窗必须把后果写在按钮上方**：这是一步会**放弃产出并触达新的开销**的操作，不能只写"确认跳过吗"。

  ```
  跳过 s2 之后：它会被记为「你已跳过」，依赖它的步骤会带着"缺了 s2"的标记继续跑，
  并因此产生新的开销。这一步的产出不会再补。
  ```

- 跳过是不可翻案的，所以被 `user` 跳过的卡片**不再给"跳过"按钮**（给了等于提供一条死路）。
- `skipKindLabel` 多一个 `user: '你已跳过'`，报告与界面共用同一套措辞。

## 十七、第六轮：同一份数据的**第二个消费者**（含一处我自己造成的回归）

前五轮都在修"某一层说了假话"。这一轮修的是另一种形状：**话改对了，但只改给了一个听众。**

引擎每次运行有两条出口 —— 一份**报告**（`trace.js` → `.md`）和一行行**终端输出**（`cli.js` → 屏幕）。报告又给界面和 CLI 两个消费者读。前五轮所有改动都落在报告那一侧，于是 CLI 那一侧**同时**留下了三处已经"修好"的病。

### 17.1 ★★ 命令行是第二份手写实现

`cli.js` 里自己写了一句：

```js
const fmtCost = (usd) => `$${(usd || 0).toFixed(4)}`
```

第三轮整轮（第十四节）在修的就是"把**没上报**印成 `$0.0000`"——报告侧改成了 `costCell()`（三态：美元 / 积分 / 未知）。但 CLI 这句是**另一份独立实现**，没跟着改。同一份数据、同一时刻：

| 出口 | 印出来的 |
|---|---|
| 报告（已修） | `花费 未折算成美元（2 个子任务按积分计费，合计 0.315296 积分）` |
| 命令行（没修） | `✓ s1 ok · 0ms · $0.0000` |

一个 qoder 全程跑完的任务，屏幕上每一行都是 `$0.0000`，那 0.157648 积分**一次都没出现过**。

修法不是"在 CLI 里再写一遍正确的格式化" —— 那只会让下一次漂移更难发现。改成**把格式化函数导出、两边共用**：

```js
// trace.js 现在导出
costOf(cost)        // 只吃 cost 对象 —— 命令行手上只有 evt.cost，没有完整 entry
costCell(entry)     // 单条（未执行 → "—"）
costTotalCell(s)    // 汇总（四态）
skipCell(s)         // 「未执行」那一格
durationCell(s)     // 「总耗时」那一格
```

`costOf` 是从 `costCell` 里抽出来的那一层，因为两边的输入形状不同。**一份格式化只留一份** —— 这个仓库在这件事上已经付过一次学费（`WRITE_PERMISSIONS` 定义在两处，导致"采集了但判定不认"）。

### 17.2 ★★ 一处我自己造成的回归：`trace.finish()` 被搬走了

第五轮抽 `advance()` 时，`run()` 结尾是这三行：

```js
trace.finish()
onEvent({ type: 'plan-finish', summary: trace.summary })
return { trace, ctx }
```

我把 `advance()` 抽出去、又给 `resume()` 写了同样的收尾，**却把 `run()` 上的那两行一起搬进了 `resume()`**。于是整单首跑之后：

- `trace.finish()` 从未被调用 → `finishedAt` 恒为 `null`、`durationMs` 恒为初始值 `0` → **报告印「总耗时 0.0s」，说"这次跑完用了 0 秒"**
- `plan-finish` 事件永不发出 → **命令行的完成汇总行、界面的「全部结束：…」都不触发**。CLI 跑完只印一行"轨迹报告：路径"，得自己打开文件才知道成没成

**整整两轮没人发现**，因为没有任何一条断言碰过 `finishedAt`、`durationMs` 或 `plan-finish`。它是最典型的"重构事故"：搬走的是一行**看起来属于收尾、但其实属于 run() 路径**的代码，编译器不管、测试不管，只有真跑起来看报告才看得见 —— 而报告里 `0.0s` 恰好和"跑得很快"长得一样。

现在三处一起堵：

1. **修回去**：`run()` 恢复 `finish()` + `plan-finish`，`resume()` 保留自己那份。
2. **让"没测到"显形**：新增 `durationCell()` —— `finishedAt` 为空时印「未知（运行没有正常收尾）」，不许印 `0.0s`。和花费那一格同一条规矩：**`0` 不是测量值。**
3. **补断言**：`orchestrator.test.mjs` 两条（收尾 + 发事件），反证 #22 / #23 分别钉它们。

### 17.3 报告里有的警告，另外两个出口也得有

`toMarkdown` 把 `degradedCount`（带缺口）和 `suspectCount`（产出可疑）当**成对**警告：

```
> ⚠️ 其中 1 个是在上游有缺口的情况下跑的 —— 成员本身正常，但输入少了一块，所以结论不完整。
> ⚠️ 其中 1 个产出可疑 —— 进程正常退出（退出码 0），但内容不像是有效结果。「成功」只说明没崩，不说明事办成了。
```

- **CLI 只有前… 一个都没有** —— 都只印了个条数。现在两条都补齐。
- **界面任务头只有「带缺口」徽章，没有「产出可疑」** —— 于是 3 条产出全部可疑的任务，在头部看起来是干净完成的（单卡片上的 ⚠️ 得逐张翻才看得到）。现在两者共用同一个 `.badge.warn`（琥珀**虚线**，不是红色 —— 红的会让人以为"跑挂了"，而这两件事该引起的反应完全不同：前者要去看结论的前提，后者要去重试）。

### 17.4 命令行日志搬进独立模块（它终于能被测了）

这块逻辑原来写在 `cli.js` 里面。而 `cli.js` 是个脚本 —— **import 它就会跑 `main()`**，所以它从来没有被任何测试碰过。这正是那个 `$0.0000` 能活下来的原因：不是没人想测，是**没法测**。

现在搬到 `src/report/logger.js`，配 `tests/cli-logger.test.mjs`（13 条），断言全部落在**最终印出来的那串字**上 —— 用户只能看见这个，中间调了哪个函数他看不见。

同时顺手删掉两个东西：`cli.js` 里那个 `fmtCost`（修完之后它没有任何调用点，**死代码是负债**），以及**收尾决定的**事件处理 —— `resume-start` / `subtask-member-changed` 在 CLI 里永远不会触发（CLI 没有重试入口），写进去就是又一批死代码。测试里专门断言了"这两个事件一个字都不印"。

### 17.5 反证（本轮 6 轮 / 9 条断言承重）

| # | 拆掉什么 | 变红 |
|---|---|---|
| 21 | 命令行退回手写 `$${(usd \|\| 0).toFixed(4)}` | 2 条（命令行） |
| 22 | 拿掉 `run()` 的 `trace.finish()`（**复现那次回归**） | 2 条 ★★ |
| 23 | 拿掉 `run()` 的 `plan-finish` | 1 条 ★★ |
| 24 | 命令行丢掉「带缺口」警告 | 1 条（命令行） |

> 断了 `finish()` → 耗时是假的；断了 `plan-finish` → 完成行根本不出现。
> 一个断言只钉一件事，反证才分得清是哪件坏了。

### 17.6 写断言时踩的坑：不许依赖"跑得够慢"

新加的收尾断言里我一开始写了：

```js
assert.ok(trace.summary.durationMs > 0, '耗时不许停在初始值 0')
```

**它挂了** —— 桩成员在同一毫秒内就结束了，`0` 是它的**真实值**。

问题不在桩太快，在断言本身：`durationMs === 0` 是个**歧义值**，「没测到」和「确实不到 1 毫秒」都可能是 0。区分这两者的唯一判据是 `finishedAt`，而"耗时是算出来的、不是停在初始值"要用**结构**来证：

```js
assert.equal(trace.summary.durationMs, trace.finishedAt - trace.startedAt)
```

没算过的话这个式子会是 `NaN`，或者两边对不上。**断言依赖时序/速度 = 断言会随机地骗人。**

## 十八、第七轮：从"有个界面"到"有个能双击的应用"

### 18.1 壳的三条设计决定

| 决定 | 为什么 |
|---|---|
| **子进程 + 读它的输出拿端口**，而不是壳自己挑端口 | `ui/server.js` 有"端口被占就顺延"的逻辑。壳再挑一次就变成**两处各自决定端口** —— 这个仓库已经在 `WRITE_PERMISSIONS` 上吃过一次"一份逻辑两处实现"的亏 |
| 子进程用 `ELECTRON_RUN_AS_NODE=1` 启动 | `process.execPath` 是 **electron.exe**，它默认会把自己当 Electron 应用启动。不设这个变量的表现是**子进程秒退且没有任何输出** |
| 不用 electron-builder，直接拷 Electron dist | Electron 官方发行包本身就是便携的：`resources/app` 放代码、exe 改个名就是成品。本机有火绒，npm 系打包工具会去下 nsis/wincodesign，动辄几十分钟还会中途 `os error 5` |

### 18.2 沙箱里必须关 GPU，而且 `--disable-gpu` 单独不够

不关的话连窗口都活不到渲染：

```
GPU process exited unexpectedly: exit_code=-1073741819
FATAL:content\browser\gpu\gpu_data_manager_impl_private.cc:416] GPU process isn't usable. Goodbye.
```

`--disable-gpu` 只关**加速**，Chromium 仍会去派生那个注定失败的 GPU 子进程。四个一起上才行：

```js
app.disableHardwareAcceleration()
app.commandLine.appendSwitch('disable-gpu')
app.commandLine.appendSwitch('disable-gpu-compositing')
app.commandLine.appendSwitch('in-process-gpu')   // ← 关键
app.commandLine.appendSwitch('no-sandbox')
```

只在 smoke 模式下启用 —— 用户正常双击时该有的硬件加速一点都不少。

### 18.3 ★★ 三条"假绿"，全是同一类：**断言被占位值满足了**

这一轮最值钱的不是打包成功，是**三次"测试全绿但什么都没验到"**，全都撞在同一件事上。

**① DOM 断言跑在了上一张页面上。**

`win.loadURL(url)` 是异步的，我没 `await` 就继续往下断言。于是断言读到的还是那个"正在启动…"占位页。
可它**大部分是绿的** —— 因为界面的静态 HTML 里本来就有 `.topbar .brand`、`#chatList`、`#memberCount`。
「界面渲染出来了」这条是在**一行脚本都没执行**的情况下通过的。

**② `0/0` 满足 `/^\d+\/\d+$/`。**

成员数那条断言原本只卡**形状**，而静态 HTML 里写死的占位值恰好是 `0/0` ——
格式完全合法。断言全绿，证明的只是"页面上有个长得像 N/M 的字符串"。
改成 **总数必须非零**之后才有意义（真值是 `3/6`）。

**③ `walk()` 返回的是相对子目录的路径，我却拿它去拼包根目录。**

打包脚本的 manifest 因此**悄悄变成了 1 个文件**。于是：

```
✓ 哈希比对：1 个代码文件逐一核对通过     ← 只比了 1 个
✓ 依赖闭包检查：0 处引用，全部能找到     ← 0 处引用，等于没查
```

**两条"通过"其实什么都没查。** 补了一道下界守卫（manifest < 10 就报错）之后才暴露出来：
真实是 21 个文件、46 处引用。

> 三次是同一个病：**能被"空集合"或"占位值"满足的断言等于没写。**
> 修法不是加强断言措辞，是**换一个只有真数据才能满足的判据** ——
> 布局用 `getBoundingClientRect()` 的非零尺寸、成员数用非零总数、manifest 用文件数下界。

### 20.2 实测矩阵（2026-09-29）

| 成员 | readonly 传下去的参数 | 与 plan 是否一样 |
|---|---|---|
| claude | `--permission-mode dontAsk` | 否 |
| cursor | `--mode ask` | 否 |
| qoder | `--permission-mode dont_ask` | 否 |
| **trae** | `[]`（什么都不传） | **是** |
| doubao | 无此概念（REST 成员，连参数都没有） | — |
| **dsh** | `[]`（四档全一样） | **是** |

三个病，全部由同一句代码引起（claude.js 与 generic.js 里各抄了一份）：

```js
return map[level] || map[this.spec.defaultPermission] || []
```

1. **静默回落**：请求的档位没配 → 拿默认档的参数顶上，界面仍显示用户选的那一档；
2. **档位塌缩**：配成 `[]` 等于"这一档不传任何参数" —— 界面上「只读 —— 能读，不改文件」
   的承诺在 trae 身上是**空的**；
3. **采集判定只信请求档**：`WRITE_PERMISSIONS.has(permission)` 决定要不要采集文件改动。
   于是 trae 的只读档**既不采集也永不判定** —— 成员真写了文件没人知道，而判定层因为
   拿不到数据（null）永远沉默。**静默失效比误报更糟。**

反向的病也有一个：**豆包**（REST 成员，没有文件系统能力）在写档下会被照做目录快照，
采集恒为空数组 —— 而空数组在判定层的意思是"采集过、确实没改"，于是豆包产出里写一句
"已创建文档"就被判可疑。**拿一把量不到东西的尺子去定罪。**

### 20.3 修法：把「档位有没有生效」变成可计算的事实

- `base.js` 新增 `describePermission(spec, level)`：返回 `{ args, source: exact|fallback|none,
  effectiveLevel, expressible }`。两个适配器的 `permissionArgs()` 改为共用它（一份逻辑）。
- `base.js` 新增 `isWriteCapable(spec)`：显式 `writeCapable` 优先，缺省按 capabilities 推断。
  **「不知道」的默认方向是 true（可能写）** —— 判 false 会让引擎跳过采集、静默失效；
  判 true 最多多跑一趟快照。代价不对称，往贵的那边保守。豆包在 members.json 里显式
  `"writeCapable": false`。
- `quality.js` 新增 `memberMayWrite(spec, level)`：**采集与定罪共用这一个判据**。
  写档 → 是；档位无法表达 → 保守按"可能写"；只有"没有写能力"或"真有参数在约束"才敢说不。
- `orchestrator.js` 的 `willTrack` 改用它，并把同一个 `mayWrite` 传给 `judgeOutput`
  （两处必须同一份，否则"采集了但判定不认"）。
- `ui/server.js` 把 `writeCapable` + `permissionSupport` 透给界面；
  `ui/public/app.js` 在 composer-hint 与协同计划弹窗里**如实提示**
  「⚠️ Trae 没有「只读」档对应的参数 —— 这一档对它们不生效」。

### 20.4 界面提示的另一半规矩：正向对照

该警告时必须警告，**不该警告时一句都不许多说** —— 每条断言都配了正向对照
（claude 四档齐全 → 不许出现警告元素）。变异验证（把两个提示函数改成"永远警告"）
证明这五条全承重 —— **一个永远显示警告的提示会被立刻当成噪音忽略掉，那不如不提示。**

### 21.2 ★ DSH 的权限档位：上一轮的结论是错的，这轮实测推翻

上一轮的审计矩阵写着「dsh 四档全 `[]` —— 档位无法表达」。**那是看错了地方。**

取证链：

1. `dsh --profile headless --help` —— 确实只有 `-h`，**没有任何权限开关**。到这一步为止都对。
2. 但 `dsh --profile headless --dump-config` 里写着：

   ```yaml
   - id: sandbox-policy
     config:
       mode: !!js process.env.DSH_PERMISSION_MODE ?? 'workspace-write'
   - id: approval
     config:
       policy: !!js (process.env.DSH_PERMISSION_MODE ?? 'workspace-write') === 'danger-full-access' ? 'never' : 'ask'
   ```

   **权限走环境变量，不走命令行参数。**

3. 实测三件事（真调 dsh，每次几秒）：

   | `DSH_PERMISSION_MODE` | 任务：读文件 | 任务：创建文件 |
   |---|---|---|
   | `read-only` | 读到了 | **被拒**：`[sandbox: file access denied under read-only mode]`，文件确实不存在 |
   | `workspace-write`（默认） | — | 成功 |
   | `danger-full-access` | — | 成功（审批 never） |

4. **最有价值的一句是 dsh 自己说的**：提权时「需要审批，而当前没有可用的审批通道 ——
   无应答者时按 fail-closed 处理」。也就是 **headless 里的 dsh 永远不会偷偷越权**，
   它宁可失败。这让"full 档"成为唯一能越出工作区的一档，也正因如此最该慎用。

**实现**：

- `members.json` 给 dsh 加 `permissionEnv`（四档 → `DSH_PERMISSION_MODE`）。
- `base.js` 的 `describePermission()` 同时看 `permissionArgs` 与 `permissionEnv`，
  `expressible = args.length > 0 || Object.keys(env).length > 0`。
  **参数与变量都查过，才允许说"这一档表达不了"。**
- `generic.js` / `claude.js` 新增 `permissionEnv()`，`run()` 里
  `env: { ...spec.env, ...permissionEnv(level) }` 真的传给进程。
- `exec.js` 的 `mergeEnv()`：值是 `null` → **从环境里删掉**（用于摘掉继承来的同名变量），
  值统一 `String()` 化（配置里写数字是自然的写法，但 spawn 只吃字符串）。

### 21.3 ★ 环境变量不参与档位回落 —— 授权只许往窄的方向给

参数回落（拿默认档的参数顶上）是既有行为，界面会警告。但**环境变量是授权，不是请求**：
把 B 档的授权拿去顶 A 档，方向正好是危险的那边 —— 用户点「只读」，却拿到执行档的写权限，
而界面上还写着"只读"。所以：**环境变量只认"这一档有专属配置"，绝不回落**（`env: {}`）。

### 21.4 塌缩的两种：合理的与危险的

dsh 的 readonly 与 plan 是同一个沙箱档（`read-only`），四档实际**三组** ——
但这**合理**：计划档的语义就是"只把方案想清楚、不动手"。
`tests/permission.test.mjs` **故意不断言"四档必须互不相同"** —— 那会逼着实现编一个假区别来讨好测试。
要钉的是**方向**：写档决不许落在只读沙箱里（`assert.notEqual(sandboxOf(lv), 'read-only')`，写档两条 + 至少三组）。

## 二十二、第十轮：把 Codex 自己接进来（2026-10-02）

用户原话：「把你自己也加进去」。加进来的就是**写这个工具的 Codex**——
Codex 桌面版自带的那份 CLI（`codex-cli 0.159.2`）。

### 22.1 为什么不能用通用适配器

`codex exec --json` 的输出是 **JSONL**：一行一个事件，不是一份 JSON 文档。
通用适配器的 `outputFormat=json` 走的是 `JSON.parse(整个 stdout)`，对这个形状必然抛错，
然后**静默退回纯文本**——正文被一整屏事件噪音包住、token 统计全丢，
而且从结果上看不出是"解析失败"。所以单开了 `src/adapters/codex.js`。

### 22.2 四个坑（都有真样本：`tests/fixtures/codex-exec-ok.jsonl` / `-failed.jsonl`）

1. **stdin 有内容时会先印一行非 JSON**：`Reading additional input from stdin...`。
   逐行解析时先跳过非 JSON 行，否则第一行就把解析带崩。
2. **item 级 `error` 不等于失败**。成功运行里也会出现——
   例如 `Model metadata for xxx not found`（模型元数据告警）。拿它判失败会大面积误报。
3. **真失败长在 turn 级**：`turn.failed`，或**不带 item 的** error 事件，配合退出码非 0。
4. **命令退出码非 0 也不等于这一步失败**。agent 常试探性地跑一下、被沙箱拒掉，
   然后把结论照样写清楚——这类运行整体是成功的。

> 一句话：**只有 turn 级的信号才算失败**。前面三条都是"看着像失败"的假信号。

### 22.3 权限档位的实测口径（和界面上那句话不一致，必须记住）

`readonly` 与 `plan` **都映射到 `-s read-only`**。该档下实测：

- 命令**能跑**（agent 可以读文件、跑只读命令）；
- **写文件被拒**。

所以界面上「只读 = 不跑命令」这条说明**对 codex 不成立**——只读挡的是写，不是执行。

其余两档：`execute` → `-s workspace-write`，`full` → `-s danger-full-access`。

### 22.4 路径要能自愈

Codex 每次自更新都会换一个哈希目录：
`%LOCALAPPDATA%\OpenAI\Codex\bin\<hash>\codex.exe`。
只写死 `command` 的话，一次自更新就会让成员变成"找不到"。
所以配置里另加了 `commandSearch`（多条通配路径，取 mtime 最新的那个）。

### 22.5 两个刻意的不做

- **`changedFiles` 保持 `null`**：codex 通过 shell 命令改文件，而不是吐 `file_change` 事件，
  凭空猜风险更大。交给引擎自己的目录快照去采（第十三节），界面显示「未采集」而不是「零改动」。
- **成本只记 token，不估美元**：订阅制下把 token 折成美元就是编数字。

### 22.6 调用形状

```
codex exec --json --ephemeral --color never --skip-git-repo-check -s <sandbox> -C <wd> -
```

末位的 `-` 表示 prompt 从 stdin 读。`--ephemeral` 不留会话记录——
成员调用是一次性的，不该往用户的历史里塞。

### 22.7 顺带修掉的一处假绿

加成员时把界面冒烟里 7 处硬编码的 `6` 改成了从 `members.json` 读的 `TOTAL_MEMBERS`。
其中两处写在**浏览器里执行**的断言片段里（`cdp.eval` 的模板字符串），
Node 这边的常量在那边的作用域里根本不存在——冒烟跑起来直接
`ReferenceError: TOTAL_MEMBERS is not defined`。
教训与第 8 节同源：**能读到配置不等于能被断言读到**；
改完必须真跑一遍，不能只看"改成变量了"。

## 二十三、第十一轮：答完即收工 —— codex 每次调用白等 10 秒（2026-10-02）

用户原话：「太慢了，能不能提一下反应速度」。

先量，再改。实测（同一台机器、同一句「只回复两个字：收到」）：

| 环节 | 耗时 |
|---|---|
| 服务就绪（含进程启动） | 171ms |
| `GET /` | 4ms |
| 成员探活（冷启动，7 个并行） | 1619ms |
| `GET /api/tree` | 9ms |
| `/api/chat` claude | 1874ms |
| `/api/chat` **codex** | **21369ms** ← 大头 |

### 23.1 时间线：答案早就有，进程不走

把 codex 的原始事件流打上时间戳，一眼就看出问题：

```
+   186 ms  thread.started
+   205 ms  turn.started
+  1857 ms  turn.completed     ← 答案在这之前就吐完了
+ 11879 ms  exit code=0        ← 白等约 10 秒
```

那 10 秒里 codex 什么也不干，只是**不肯退出**；而成员调用是串在用户等待路径上的，
用户就实打实等掉这 10 秒。

### 23.2 改法：接到收尾事件就按**进程树**收工

- `exec.js` 新增 `opts.stopWhen(line)`：逐行扫 stdout，命中即收工，并回报 `stoppedEarly: true`。
- codex 适配器传的判定是 `isTurnEndLine` —— **只认 `type` 字段**（`turn.completed` / `turn.failed`），
  不在整行里搜字样：agent 正文里出现"这串字符"是可能的，拿它当收尾信号会把真正的交付切掉。
- 收工用 `taskkill /PID <pid> /T /F`，不是 `child.kill()`。

### 23.3 为什么必须按进程树收工

`shell: true` 起的 child 是 `cmd.exe`，真正的 CLI 是它的子进程。`child.kill()` 只杀 `cmd.exe`，
留下一个 138MB 的 `codex.exe` 挂在后台 —— 而它会**向上找正在运行的 Codex 桌面版**，两边互相干扰。
实测 `taskkill /T /F` 能把整棵树收干净（turn 结束 2017ms → close 2249ms，无残留）。
测试里有一条断言专门盯这个：收工 0.5 秒后拿子进程 pid 去探活，必须已经不在。

### 23.4 ★ 最容易安静记错的一处：退出码

`taskkill /F` 会让进程以**非 0** 退出，而 codex 的判定里"退出码非 0"本来是失败信号之一。
不处理的话，每一次"答完就收工"的正常运行都会被记成 `failed` —— 不报错、不崩，只是报表全错。
所以 `resolveOutcome` 收到 `stoppedEarly: true` 时**不拿退出码定罪**；真的 turn 级失败不受影响
（它走 `turn.failed` / turn 级 error 两个信号）。三条断言钉住这个方向：`stoppedEarly` 时非 0 退出码 → ok；
`stoppedEarly` + 真 turn 失败 → 仍然 failed；没有 `stoppedEarly` 时非 0 退出码 → 照旧 failed。

### 23.5 半行不判

逐行扫描只在**整行凑齐**之后才判。判定函数拿到半行 JSON 必然解析失败 ——
那表现是"优化看着生效了、其实没有"，属于最难发现的那种坏。扫描挂在已有的那个 stdout
监听器里，**不另加监听器**：两个监听器各存各的缓冲与游标，早晚分叉，而分叉的时机取决于分片大小。
