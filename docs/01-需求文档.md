## 0. 一句话目标

把本机已有的 AI agent 统一接入同一个工作台，**由 WorkBuddy 当主脑做任务拆解与角色分配**，其他成员当执行手；每个成员既能单独开一个会话面板使用，也能组成一条自动协同的流水线。

## 2. 核心概念

| 概念 | 定义 |
|---|---|
| **主脑（Orchestrator）** | 唯一的核心调度者，固定为 WorkBuddy。负责理解目标 → 拆子任务 → 分派成员与角色 → 决定依赖顺序 → 汇总成果 |
| **成员（Member）** | 一个可被调用的 agent。有 id、显示名、启动方式、能力标签、权限换算规则 |
| **任务（Task）** | 用户提出的一个目标 |
| **子任务（Subtask）** | 主脑拆出的最小执行单元，绑定「一个成员 + 一个角色 + 一段 prompt + 一组输入产物」 |
| **角色（Role）** | 子任务里的分工标签，如 `代码主笔` / `文档书写` / `评审` / `测试`。由主脑**运行时决定**，非预设死 |
| **成果物（Artifact）** | 子任务产出，分文件类（改了仓库文件）与文本类（一段文字/报告） |
| **会话面板（Session Panel）** | 独立使用模式下的最小界面单元：一个成员 + 一段对话上下文 |
| **运行轨迹（Trace）** | 任务完整执行记录：谁在何时收到什么、输出什么、耗时、是否报错 |

### 3.2 本机环境的两个坑（适配器必须处理）

1. **Git Bash 不认 `.cmd` 扩展名**
   `command -v claude` 返回 not found，实际文件是 `claude.cmd`。
   → 适配器里**必须写全扩展名**，或显式调用 `cmd.exe /c`。

2. **claude CLI 启动时会触碰 `reg.exe`，被本机安全策略拦截**
   实测每次执行 `claude --help` 都会附带一条 `reg.exe` 被拉黑的告警（沙箱层面拦截）。
   当前不影响输出结果，但**通过 Electron 应用（非沙箱）调用时需复测**，可能表现为启动变慢或告警。

### 3.3 Claude CLI 已探明的能力（实测自 `claude --help`）

| 我们需要的 | Claude 对应参数 |
|---|---|
| 静默执行 | `-p, --print` |
| 结构化输出 | `--output-format text \| json \| stream-json` |
| **权限三档** | `--permission-mode`：`plan`／`acceptEdits`／`bypassPermissions`／`manual`／`dontAsk`／`auto` |
| 指定模型 | `--model <alias\|full-name>` |
| 附加工作目录 | `--add-dir <dir>` |
| 注入角色设定 | `--append-system-prompt <prompt>` |
| **成本上限** | `--max-budget-usd <amount>`（仅 `--print` 下有效） |
| **强约束结构化输出** | `--json-schema <schema>` |
| **后台长任务** | `--bg` 起后台会话，`claude logs` / `claude attach` / `claude stop` 管理 |
| 会话续接 | `-c, --continue` / `-r, --resume <id>` / `--fork-session` |
| 工具白/黑名单 | `--allowedTools` / `--disallowedTools` |

**权限档位映射（已确定可直接落地）**

| AgentHub 档位 | Claude `--permission-mode` |
|---|---|
| 只读 | `dontAsk`（需授权的动作自动拒绝） |
| 计划 | `plan` |
| 执行 | `acceptEdits` |
| 全自动（可选，默认关） | `bypassPermissions` |

> `--bg` + `claude logs` 是个意外收获：长任务可以交给 Claude 自己管后台会话，我们不用手写子进程保活逻辑。

### 4.2 豆包的硬限制

它只是一个模型 API，**没有文件读写和 shell 能力**。所以只能承担纯文本角色：文档书写、翻译、摘要、评审意见、文案。这正好落在你说的"谁为文档书写"上——但这也意味着**别指望它改代码**。

## 5. 功能需求

### FR-1 成员接入层（适配器模式）

- 每个成员一个适配器，对外统一接口：
  `run(member_id, prompt, workdir, permission_level, context) -> Result`
- 统一结果结构：`status` / `text_output` / `changed_files[]` / `cost` / `raw_log`
- 适配器**必须可独立调用**（这是"单独使用"的底座）
- 新增成员只需加适配器 + 一行配置，引擎不动

### FR-2 独立使用模式（每个成员单独一个会话面板）

- 侧边栏可为**任意成员**新建独立会话面板，不经过主脑
- 一个成员可开多个面板，上下文互相隔离
- 面板内保留该成员的完整对话历史，可续接、可回溯
- 独立面板与协同任务**共用同一套权限档位、日志体系和成本统计**
- 面板头部显示：成员名 / 当前模型 / 权限档位 / 本次会话已花费

### FR-3 主从编排引擎（核心）

```
用户给目标
   ↓
主脑（WorkBuddy）理解目标 + 读取项目上下文
   ↓
拆成 N 个子任务：成员 / 角色 / prompt / 依赖 / 期望产出
   ↓
渲染成「执行计划表」→ 你确认（按权限档位）→ 开始调度
   ↓
按依赖顺序调度，无依赖的并行跑
   ↓
收集成果物 + 状态；失败则重试 / 换人 / 上报
   ↓
主脑汇总成最终交付物 → 落盘 → 生成轨迹报告
```

必须支持：
- **依赖编排**：子任务 B 可用 A 的产出当输入（"谁主笔 → 谁写文档"靠这个实现）
- **并行执行**：无依赖子任务同时跑
- **失败策略**：超时 / 非零退出 / 无输出三类分别处理，重试次数可配
- **中途干预**：可在子任务边界暂停，让你改指令、换人、跳过

### FR-4 上下文与成果物管理

- **共享工作目录**：成员在同一项目目录下工作，靠读文件自然获得上下文
- **任务简报文件**：每个子任务生成 `TASK.md`（目标 / 约束 / 上游产物路径），放进工作目录让成员自己读
- **成果物收集**：跑完 diff 出改动文件，快照存档，可按子任务回溯
- **冲突处理**：并行写文件的子任务默认**不共享目录**，改用隔离副本（Qoder 支持 `--worktree`）；仅串行依赖的才共享

### FR-5 权限与人工介入

对外三个档位（映射规则见 §3.3）：

| 档位 | 行为 |
|---|---|
| **只读** | 只分析、只出建议，绝不落盘 |
| **计划** | 给方案，你确认后才落盘 |
| **执行** | 直接改文件，只在危险动作前拦 |

- 可**按任务设**，也可**按成员设**（如 Cursor 允许直接写、Trae 只允许出计划）
- 危险动作至少拦住：删文件、`git push`、装依赖、访问工作目录之外

### FR-6 自定义成员（可自加）

配置文件 `members.json`：

```json
{
  "id": "my-agent",
  "name": "我的 Agent",
  "command": "myagent.cmd",
  "args": ["-p", "{prompt}"],
  "workdirFlag": "-w",
  "outputFormat": "text | json | stream-json",
  "permissionFlags": { "readonly": [], "plan": ["--permission-mode","plan"], "execute": ["--yolo"] },
  "capabilities": ["code", "shell"],
  "env": { "MY_API_KEY": "${MY_API_KEY}" }
}
```

- 新成员接入**不改代码**，改配置即可
- 密钥只走环境变量引用，**不落明文**

### FR-7 可观测性

- 每个子任务：完整命令行、stdout/stderr 原文、耗时、退出码
- 每个任务：一张执行轨迹（谁→谁→谁、各耗时、哪步失败）
- 日志按任务分目录存盘，可导出
- 实时显示每个成员状态（排队 / 运行中 / 已完成 / 失败）

### FR-8 任务历史与模板

- 保留历史任务，可重跑、可复制某条子任务的命令
- 可把跑通的一次编排**存成模板**，下次直接套

## 6. 非功能需求

| 项 | 要求 |
|---|---|
| **平台** | Windows 11 优先，架构上不排斥跨平台 |
| **本机兼容** | 必须绕开火绒、`reg.exe` 拉黑、Electron 沙箱限制、`.cmd` 扩展名问题 |
| **长任务** | 子任务可能跑十几分钟，MCP 回传必须**异步轮询 + 进度推送**，不能同步等 |
| **可中断** | 任何时刻能停掉某个成员，且不留孤儿进程 |
| **密钥安全** | API Key 只走环境变量，不进配置、不进日志 |
| **离线降级** | 某 CLI 不可用时明确显示"不可用+原因"，不影响其他成员 |
| **成本控制** | 每个成员可设单次任务的 token/金额/时长上限 |

## 7. 技术架构（A 方案落地）

```
┌─────────────────────────────────────────────┐
│              WorkBuddy（主脑）                │
│  读取项目 / 拆任务 / 分派 / 汇总 / 写文档       │
└──────────────────┬──────────────────────────┘
                   │ MCP 协议
                   ▼
┌─────────────────────────────────────────────┐
│            Electron 应用（AgentHub）          │
│   MCP Server ← 暴露工具给 WorkBuddy           │
│   编排引擎（调度/依赖/重试/权限）               │
│   适配器层（每成员一个）                        │
│   会话面板管理（独立使用模式）                   │
│   工作目录与成果物管理                          │
│   监控台 UI                                   │
└──────────────────┬──────────────────────────┘
                   │ 起子进程 / HTTP
                   ▼
   Claude CLI · Cursor CLI · Qoder CLI ·
   Trae CLI · 豆包 API
```

### MCP 工具设计（初稿）

| 工具名 | 作用 |
|---|---|
| `list_members` | 返回所有成员、状态、能力标签、是否可用 |
| `dispatch_task` | 提交子任务给指定成员，立即返回 `task_id`（异步） |
| `get_task_status` | 查询子任务状态与进度 |
| `get_task_result` | 取结果（文本 + 改动文件清单） |
| `run_collaboration` | 提交完整协同流程（目标 + 成员 + 权限档位），主脑拆解后执行 |
| `get_collaboration_report` | 取整个流程的轨迹报告 |
| `cancel_task` | 中止某子任务 |

> `dispatch_task` 与 `run_collaboration` **必须异步**——立即返回 id，靠轮询拿结果，避免 MCP 调用超时。
